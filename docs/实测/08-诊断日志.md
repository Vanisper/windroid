# 诊断日志原生验收

2026-11-21，Apple M4、10 核、16 GiB、macOS 27.2.1。用全新工作区的签名 Windroid 客户端和 Android Emulator 37.2.13 验收。以下时间取自采集记录。界面核查使用指定 Windroid PID 的 macOS 辅助功能树，核对日期、启动标识、来源、文本与序号。[设计及实现](../架构/诊断日志.md)

## 一个 Windroid 和一个模拟器连续经过午夜

原生确认建库后创建两台 phone-1080 实例，均为 Google Play ARM64 API 33 r9、2 核、2048 MiB、8 GiB。给随后启动的 Windroid 及其子进程固定 `TZ=WQA-02:55`，即 UTC+02:55。2026-11-20 21:05 UTC 是该进程时区的 11 月 21 日零点。验收中宿主系统始终沿用原设置。

| 来源 | 当次身份 | 午夜前最后一条 | 午夜后第一条 |
|---|---|---|---|
| Windroid | PID 82864，`2ce504fb09a76911583822610c88d538` | #6，11-20 23:57:52.204，批量调度记录 5554/5555 被占用 | #7，11-21 00:00:05.902，收到另一台模拟器的退出码 0 |
| Android 2 | QEMU PID 82995，`4b8ef99e47aa263902ad60210c9bc440` | #104，11-20 23:57:31.037，stdout，模拟器报告调整屏幕超时与 logcat 缓冲 | #105，11-21 00:00:03.073，stdout，模拟器报告等待 PID 82995 优雅退出 |

两条模拟器文本都来自实际 stdout。午夜后点击「停止实例」，随后还有保存快照的输出，#113 为 Windroid 取得的退出结果。退出客户端后，两份清单均有结束结果。附件保留了两份清单、选取的完整 JSONL 行，以及重开客户端后从原生控件读回的对应行。[原始记录与界面摘录](附件/08-跨日与拦截.json)

- **设置 → 应用日志**：11 月 20 日的跨日周期为 #1–6，11 月 21 日为 #7–9。点该次启动后，两个日期和 #1–9 在同一视图可读。
- **管理 Android 2 → 更多 → 模拟器日志**：分别进入两天的日期视图，次日只有该周期的 #105–113。进入按启动视图逐页读回 #1–24、#25–48、#49–72、#73–96、#97–113，最后一页同时包含 #104 与 #105。逐页对照原生分段按钮的辅助功能值和 JSONL，两端序号连续，模拟器清单关联上述 Windroid 启动标识。

### 停机信号的复查

在首次异常的快照恢复轮次，QEMU PID 91298 报告成功载入 `default_boot`，12.8 秒后报告开始优雅停机，再过约 133 毫秒收到信号 6。另一台 PID 91513 从完成冷启动到开始停机约 29.4 秒，也以信号 6 结束。两次都没有保存快照成功的尾行。正常保存并以 0 退出的 PID 93055 同样出现了 netsim CANCELLED/GOAWAY。两个异常 PID 的用户级及系统级 DiagnosticReports 均未找到对应的调用栈。

另建隔离工作区，使用同一镜像、实例规格、端口 5556、固定时区和原生停止按钮。将标记写入 `/data/local/tmp/windroid-shutdown-check` 并刷盘，正常停机后将私有 AVD 和刷盘凭证保留为试验种子。每次在客户端退出后，把种子克隆回相同位置，再启动本轮客户端。六次定时对照使用同一个 `snapshot.pb`，SHA-256 为 `a0baa437e7f65143368d657c1692976c1884bff2528b225c3b8687cf7312b2d1`。

| 停止条件 | 功能分支 | 主线基线 |
|---|---|---|
| 看见模拟器的快照载入成功输出后等待 12 秒，再从原生面板点击停止；两个版本交替执行 | `ac13208` 三次，QEMU PID 284、1211、2099，均退出 0 | `8773493` 三次，PID 754、1705、2503，均退出 0 |
| 前期未固定延迟的快照恢复停机 | PID 96204 退出 0 | PID 96746 以信号 11 退出 |

通过当前实例的 `active.pid` 找到 QEMU，提前登记 Darwin kqueue 的 `EVFILT_PROC`、`NOTE_EXIT` 和 `NOTE_EXITSTATUS`。基线使用原版单文件采集。六次定时对照及基线信号 11 的那次停止完成后，均在恢复种子前用该轮留下的私有盘重新启动，经 ADB 核对 AVD 身份并读回原标记。原先两次信号 6 的发生时刻有记录，固定条件下未稳定复现，其内部原因和与采集方式的因果关系仍未确定。[内核退出状态与重启回读](附件/08-快照停机对照.json)

## 启动前拦截

在上述跨日 Windroid 周期，使用临时 TCP 监听器真实占用我的 Android 的 5554 端口。Android 2 继续运行。

| 入口与操作 | 重开后，在 11 月 20 日应用日志读到的记录 |
|---|---|
| 单台「启动实例」 | #5，23:57:31.895，组件「实例调度」，带我的 Android 的稳定 ID，原因是「模拟器端口对 5554/5555 已被占用」。单台失败提示的「查看启动日志」直接打开本次应用记录。 |
| 释放端口，打开「全部启动…」。预览为一台可启动、一台已运行。在确认页再次占用 5554，然后点「启动 1 个」 | #6，23:57:52.204，组件「批量调度」，同一实例 ID 与端口对原因。原生结果页显示失败 1、跳过 1。 |

两次失败的应用事件均没有模拟器启动 ID。该实例在两个拒绝之间没有模拟器进程，第二次拒绝后其目录仍只有 AVD、实例清单和现有运行锁。之后释放端口，首次真实启动才生成该实例的模拟器日志。只读预览与重新检查没有增加应用事件。[执行与预览回归](../../crates/host/src/library/tests/batch.rs)

在宿主自动化夹具中，给同名实例分别换上已满和已关闭的命令队列。经单台原生请求的路由派发启动、重新启动和冷启动，再提交同一份批量确认单。全局队列拒绝两次后仍能提交，实际派发的两项分别因队列已满、已关闭而失败。封存后用查看器的分页接口重新打开应用日志，读到 3 条单台拒绝、2 条整批确认拒绝和 2 条逐实例拒绝，每次各一条。每条实例事件均带相应稳定 ID，整批事件只属于 Windroid；所有事件的原因与队列状态相符，三台实例预先登记的启动关联均保持原值。运行 `cargo test --locked -p host --lib start_refusals_persist_once_with_their_dispatch_scope` 可复核这些结果。[队列夹具与读回断言](../../crates/host/src/library/tests/batch.rs)

## 复核步骤

1. 按[原生批量验收的隔离启动方式](07-全部实例批量启停.md#复核步骤)新建工作区、预放官方组件和镜像并启动独立 ADB 服务。打开签名包的 `Contents/MacOS/windroid`，从原生窗口确认建库并创建两台实例。
2. 为复测时段选定约三分钟后的一个 UTC 整分钟，计算一个固定偏移，让该时刻在测试进程中恰为 00:00。启动客户端前给它传入相应 POSIX `TZ`，子进程继承。在本次实测的 UTC 21:05 示例中，实际启动形如 `TZ=WQA-02:55 "$bundle/Contents/MacOS/windroid"`。
3. 午夜前启动第一台并等到就绪，在第二台上执行上述两次端口拦截。经过午夜再停止第一台并关闭客户端。用相同环境重开，检查两个原生入口；随后在该日期再次退出、重开及启停同一实例。两台顺序启动也能通过其稳定 ID 分别核对记录。
4. 对照各周期 `run.json`、两段 JSONL 与 UI。先按日期定位，再点该次启动翻页。确认退出结果、实际 stdout 或 stderr、序号及采集时的 UTC 偏移。

## 可控边界和验证范围

- 注入的记录时刻覆盖跨日半行、静默无空段、积压跨日、两个偏移不同的 01:30 和日期回拨。回到原日期后查该日得到 #1、#5，按启动则为 #1–5。半行按读到换行时的日期归档。[组行](../../crates/runtime/src/instances/collector/child.rs) · [轮转、分页与保留](../../crates/diagnostics/src/writer/tests.rs)
- 故障夹具验证实际进程创建失败、启动后无输出退出、采集器被终止后双流各 4 MiB 的持续排空，以及宿主先退出后继续收 stderr。通过缩小预算和阻塞写者验证丢失范围、容量回收及写入恢复；另验证损坏来源与健康来源的隔离。[进程故障](../../crates/runtime/tests/instances/diagnostics.rs) · [局部损坏](../../crates/diagnostics/src/writer/tests.rs)
- 机器没有实际断电、填满系统卷或经历真实夏令时切换。宿主和采集器同时消失后，后续输出没有留存保证。保留默认值尚未经过长期生产负载标定。

执行 `npm run build:ui`、`npm run check:macos` 和 `npm run test:macos`。按 Cargo 各测试目标的最终汇总，工作区常规测试 230 项通过，26 项环境专用用例标记为 ignored；其中宿主 38 项、UI 42 项、日志存储 11 项通过。严格 Clippy 覆盖全部工作区目标。用 `scripts/package-macos.sh` 生成 release 应用，`codesign --verify --deep --strict` 通过，签名为本地 ad hoc。所有改动的 Rust 文件均通过 rustfmt 检查；全仓格式检查的输出与 `8773493` 完全一致。

另用签名包运行 [工作区原生门禁](../../scripts/check-workspace-gate.py)。九类被拒绝的目录在退出后保持原样；取消或重选目录、在新位置建库、重新打开已有工作区及预放资源确认均通过。用独立的格式有效工作区，将 `logs/app` 置为普通文件，应用仍可打开和退出；原生查看器及「刷新」的辅助功能值均显示无法采集或读取的原因，生命周期事件退回标准错误，原文件内容保留。关闭标准错误管道后也复跑了写入降级用例。

另行执行环境专用的[双机停机回归](../../crates/runtime/tests/real_emulator.rs)。先启动的真实实例在 22.3 秒后就绪，第二台用时 25.9 秒。停止第一台后，连续五次观测到第二台的内核启动标识不变、三个 Android 服务就绪，路由检查通过。用例在 72.1 秒内完成。
