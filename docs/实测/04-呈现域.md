## 1. 框架选型的转折：nsh

### 背景

初期的候选是 GPUI。它有两个未验证的风险点，且都被列为**否决项**：

- 能否拦截窗口关闭（不通过就不做）
- 能否挂载原生视频表面

调研期间发现了 [longbridge/nsh](https://github.com/longbridge/nsh)（Native Shell），它从设计上绕过了这两个问题。

### nsh 是什么

Rust 优先的原生 UI 框架，Apache-2.0。用各平台自己的原生视图渲染：

| 平台 | 渲染方式 |
|---|---|
| iOS | UIKit, CoreText |
| Android | Android views, StaticLayout |
| macOS | AppKit, Core Animation, CoreText |
| Windows | Win32, Direct2D, DirectWrite |
| Linux | GTK 4, Pango |
| GPUI | GPUI（作为可选后端） |
| 终端 | ratatui |

版本 0.5.0（crates.io 上 0.5.1），2026-10 首次发布，crates.io 上月下载约 500 次。

### 两个关键机制

**1. `AppView`：引擎以 NSView 形式嵌入我们自己的窗口**

```rust
let view = AppView::new(mtm, AppOptions::default());
view.load(Root::of::<my_app::App>().into());
window.setContentView(Some(&view.view()));   // ← 窗口是我们的
```

窗口由调用方创建并持有。这不是「框架开窗口、我们想办法接管」，而是从一开始窗口就属于我们。关闭拦截回到标准的 `NSWindowDelegate`。

**2. 原生组件：注册一个名字，框架把任意 NSView 摆进去**

```rust
app_view.register_component("windroid.video", Rc::new(move |ctx| {
    Box::new(VideoSurface { view: /* 任意 NSView */, context: ctx })
}));
```

框架负责布局、裁剪、滚动、触摸分发；组件只需提供一个 `NSView`。官方文档明确说：

> Because NSH renders with the system's own views, a native component is just one more subview in the same hierarchy: there is no layering problem, it clips, scrolls and receives touches like a `<View>`.

这正是视频表面需要的形态——一个可以被布局系统摆放的 `CAMetalLayer` 承载视图。

### 与 GPUI 的对比

| 维度 | GPUI | nsh |
|---|---|---|
| 窗口所有权 | 框架持有,需找 hook | **我们持有** |
| 原生表面 | 未验证 | **原生组件机制,文档明确支持** |
| 平台渲染 | 自绘 | 各平台原生视图 |
| 许可证 | Apache-2.0 | Apache-2.0 |
| 成熟度 | 为 Zed 服务,API 变动频繁 | 0.5.x,发布一个月 |

**结论**：nsh 的架构与我们的需求同构，而且它是「原生视图 + 我们持有窗口」，比「框架自绘 + 找 hook」的路子干净得多。

**保留的顾虑**：nsh 很新（发布一个月），API 可能变动。但它有明确的向后兼容承诺（见第 4 节），且可以用 crates.io 的固定版本锁定。

## 2. Spike 1：窗口所有权与关闭拦截（PASS）

### 目标

验证「我们创建窗口 → nsh 嵌入 → 我们自己当 delegate → 拦截关闭」。

### 实现要点

```rust
// 1. 我们创建窗口
let window = NSWindow::initWithContentRect_styleMask_backing_defer(
    NSWindow::alloc(mtm), rect, style, NSBackingStoreType::Buffered, false,
);
unsafe { window.setReleasedWhenClosed(false) };

// 2. nsh 引擎嵌入
let app_view = AppView::new(mtm, AppOptions::default());
app_view.load(Root::of::<App>().into());
window.setContentView(Some(&app_view.view()));

// 3. 我们自己当 delegate
define_class!(
    #[unsafe(super = NSObject)]
    #[thread_kind = MainThreadOnly]
    #[ivars = ()]
    struct WindroidDelegate;

    unsafe impl NSObjectProtocol for WindroidDelegate {}
    unsafe impl NSWindowDelegate for WindroidDelegate {
        #[unsafe(method(windowShouldClose:))]
        fn window_should_close(&self, _sender: Option<&NSWindow>) -> bool {
            println!(">>> INTERCEPTED windowShouldClose");
            false   // 拒绝关闭
        }
    }
);
```

### 结果

```
[1] app configured
[2] window created, closable=true
[3] nsh AppView mounted into OUR window
[4] delegate set: true
[5] makeKeyAndOrderFront -> isVisible=true
[9] entering run loop
[6] before performClose: isVisible=true
>>> INTERCEPTED windowShouldClose #1 -> returning false
[7] after performClose:  isVisible=true
[8] final: visible=true intercepts=1
RESULT: PASS
```

**关键验证点**：
- `windowShouldClose` 被调用（不是被框架吞掉）
- 返回 `false` 时窗口保持可见（关闭确实被拦住）
- 引擎正常渲染（`AppView` 与自定义 delegate 可以共存）

### 踩过的坑

| 问题 | 原因 | 解法 |
|---|---|---|
| `MyDelegate: RefEncode/NSObjectProtocol/MainThreadOnly not satisfied` | 手写 `unsafe impl` 缺少宏生成的元数据 | 用 `define_class!` 宏 |
| `conflicting implementations of MainThreadOnly` | 宏内已声明 `#[thread_kind]`，又手写了 impl | 只用宏属性 |
| `setDelegate` 类型不匹配 | 需要 `ProtocolObject` 包装 | `ProtocolObject::from_ref(&*delegate)` |
| 跨线程传 `NSWindow` 编译失败 | ObjC 对象不是 `Send` | 用 `thread_local!` 保存，或在闭包内重新获取 |

## 3. Spike 2：1080p 帧上传性能（PASS）

### 目标

1080p 帧从 CPU 内存上传到 Metal 纹理的耗时，判断是否在 30fps 预算（33.3ms/帧）内可接受。

### 方法

- 创建 1920×1080 BGRA8 `MTLTexture`，`Shared` 存储模式
- 连续 90 帧 `replaceRegion` 上传，测量总耗时
- 3 帧预热后开始计时

### 结果

```
[surface] 原生组件已创建，纹理 1920x1080 BGRA Shared
[result] 90 帧 replaceRegion 上传
[result] 总耗时 32.7 ms
[result] 每帧 0.36 ms → 理论上限 2751 fps
[verdict] 30fps 预算 33.3ms/帧，上传占比 1.1%
RESULT: PASS (上传开销可忽略)
```

**每帧 0.36ms，占 30fps 预算的 1.1%。**

### 解读与边界

这个数字是**上传本身**的开销，不含：

- H.264 解码（硬件解码器，通常 1–3ms@1080p）
- 渲染提交与合成
- nsh 自身的布局与绘制

但上传是唯一由我们完全控制且可能做错的部分。0.36ms 说明**数据搬运不是瓶颈**——剩下的预算足够解码和渲染。

**未测**：端到端 30fps 的完整链路（解码 → 上传 → 渲染）。这需要真实的 scrcpy 流，属于 M1b。

## 4. nsh 的向后兼容承诺

nsh 有明确的兼容性政策（`nsh.dev/docs/compatibility`），核心是：

> an app built for a compatible release runs on every later release, unchanged. An app that stops working after an NSH update is a bug in NSH.

具体规则：
1. 已发布的 API 不移除
2. 重命名保留旧名作为 `@deprecated` 别名，永久保留
3. 类型只增不减（union 只加分支，函数只加重载或尾部可选参数）

**这个承诺覆盖的是 NSH 应用的 TSX/Rust API**。我们是用 Rust 直接依赖 crate，走的是 Rust 的语义化版本——需要自己锁 `0.5.x`。

**评价**：这个承诺的存在本身是个好信号，说明作者在认真考虑被依赖。但一个月的项目能否兑现长期承诺，只能观察。

## 6. M0 实测：TSX 工程形态与宿主通道

M0 把「窗口 + 设备域 + 界面」三者接通时发现的、与设计直接相关的事实。

### 6.1 导入路径：模块名与实际 specifier 不是一回事

界面里调用宿主，正确的写法是：

```ts
import { host } from "nsh";
```

**不是** `from "nsh/host"`。后者在 `nsh-js` 的模块表里带 `moved_to: Some("nsh")`，
其导出被合并进 `nsh`，而带 `moved_to` 的名字**不参与 specifier 解析**——写了会在
运行时或构建期找不到模块。该字段的注释原文是「it is no module apps import,
only the source of those exports and their types」。

同理，`nsh` 的顶层导出里没有 `Each`（列表虚拟化在 `nsh/list`）。列表项不用写
React 那样的 `key`：nsh 的行复用由 `Each` 的 `key` 负责，普通 `map` 加 `key`
只会得到一条 unsupported prop 告警。

### 6.2 能力门控：默认全禁，且漏声明只在运行期报错

`Capabilities::all()`（没有 `capabilities` 键时用的全开集合）里，网络、webview、
剪贴板、通知等一概放开，**唯独 `host` 是空的**。源码注释直说：「The host's functions
are never granted without a declaration.」

因此两件事都必须做对：

| 要点 | 说明 |
|---|---|
| `nsh.json` 声明 | `{"capabilities": {"host": ["windroid.*"]}}`，前缀需带 `*` |
| 能力真的随 bundle 载入 | `Bundle::source(code)` **不读** `capabilities.json` |

第二条是最容易漏的。手工拼 Bundle 必须链上 `with_capabilities_json(Some(&json))`，
否则每个 `host.call` 都被拒为 `ERR_ACCESS_DENIED`，而构建期一切正常。
用 `Bundle::read(path)` 则没有这个问题——它会一并读取同目录的 `capabilities.json`
与 source map。

**事件不需要任何 grant**：`HostChannel::send` 不受 `capabilities.host` 约束，
只有 TSX 反向调 Rust 才需要。

用 `true` 声明会展开成 `["*"]`，等于把整套宿主接口全开。用前缀更安全。

### 6.3 通道接通的判据：只调 set_params 不算

`HostChannel::set_params` 本身**不会**把通道标记为 configured。在注册 handler
或发送事件之前，`host.available()` 返回 `false`，且 `host.call` 会走到平台 host
分支并 reject `ERR_FEATURE_UNAVAILABLE_ON_PLATFORM`。

本项目的做法是：在载入界面**之前**就 `Bridge::attach`（它注册两个 handler 并
起事件线程）。顺序反了，界面首帧那次取快照会落到「没有 handler」上。

### 6.4 TSX 的状态必须放在模块级

这是 M0 里唯一一处花了几轮才定位的缺陷，值得单独记。

nsh 的 TSX 是 Solid 式的细粒度响应式。组件函数体**每次重算都会重新执行**，
因此：

- `signal` 与 `host.on` 写在组件体内 → 每次渲染新建一份状态、重复订阅一次。
  表现为「数据确实取到了，但界面不更新」。
- `const s = signal()` 写在组件体内 → 只取一次值，后续更新不反映。
  派生值必须用 `computed(() => ...)`。

定位方法：把 `host.available()` 与最近一次调用结果直接渲染到界面上。诊断显示
`ok seq=0` 说明通道与数据都正常，问题就只在响应式这一层，不必再怀疑宿主侧。

### 6.5 关闭拦截：拦得住，也要放得掉

M0 用 example 而非 test 验证（AppKit 要求主线程，测试函数拿不到
`MainThreadMarker`；同时手动泵 `nextEventMatchingMask` 让输出事件真的绘制）。

```
[1] 窗口已显示 visible=true title=Windroid Spike
[intercept] 第 1 次 windowShouldClose 被调用
[2] 第一次关闭后 visible=true  (期望 true)
[intercept] 第 2 次 windowShouldClose 被调用
[3] 第二次关闭后 visible=true  (期望 true)
[intercept] 第 3 次 windowShouldClose 被调用
[4] 第三次关闭后 visible=false (期望 false)
[5] 拦截次数=3 记录=[1, 2, 3]
RESULT: PASS
```

判据是三条同时成立：代理被调用、返回 Keep 时窗口仍在、返回 Close 时窗口真的关。
**只会拒绝的拦截器是坏的**——用户会关不掉窗口，那比拦不住更糟。

### 6.6 依赖链陷阱：rolldown 的版本范围

`nsh-bundler` 依赖 `rolldown = "=1.2.13"`，而后者依赖 `rolldown_devtools = "^1.2.13"`。
该范围会解析到 1.3.2，其又要求 `rolldown_std_utils = "=1.3.2"`，而 1.3.2 删掉了
1.2.13 需要的 `representative_file_name_for_preserve_modules`，于是编译失败。

解法是把整栈锁回 1.2.13：

```bash
cargo update -p rolldown_devtools --precise 1.2.13
cargo update -p rolldown_std_utils --precise 1.2.13
```

这是上游的版本范围缺陷，与本项目无关，但会卡住任何要用 `nsh-bundler` 的下游。

### 6.7 构建使用 nsh CLI

界面构建走 nsh 官方 CLI，不自建构建工具。

`nsh build` 与 `nsh check` 独立于 nsh 的开发宿主；官方文档对 `nsh build` 的定位
是「for apps that embed NSH and ship the bundle themselves」，正是本项目的场景。

同一份 `App.tsx` 的产物：

| 项 | `nsh build` |
|---|---|
| `bundle.js` | 7725 字节 |
| `capabilities.json` | 与 `nsh.json` 的 `capabilities` 一致 |
| `bundle.nshc` | 字节码，21 KB |
| `app.json` | app id / url scheme |
| `assets/` | 导入的图片字体 |

构建命令：

```bash
nsh check app                    # 生成类型声明 + 类型检查
nsh build app -o app/.nsh/out    # 编译界面
```

**注意**：`nsh build` 的 `-o` 相对路径以当前工作目录为基准，不是 app 目录。
不写 `-o` 时产物落在 `./.nsh/out`。

命名陷阱：crates.io 上的 `nsh` 0.4.2 是一个无关的 Rust CLI shell，
真正的 CLI 包名是 `nsh-cli`（二进制名是 `nsh`）。

### 6.8 编辑器里的类型：需要 declarations feature

**现象**：TSX 里每个 `from "nsh"` 都标红，`mount`、`signal`、`computed` 全部
「找不到名称」，而构建与运行完全正常。

**原因有两层，缺一不可**：

1. nsh 的类型声明写在 `.nsh/types`，由每次构建生成。仓库里没有这个目录，
   编辑器的 TypeScript 服务就无从解析 `nsh` 这个模块名。
2. 生成器本身需要 `nsh-core` 的 `declarations` feature。这个 feature 默认
   **关闭**，关着时 `Ts::function` 之类的构造函数返回 `Ts::Internal`，
   `type_definitions` 于是产出不含任何导出的模块文件——连 `nsh/index.d.ts`
   都不生成。表现是「补全全空」，比纯粹找不到模块更难判断。

实测对照：

| `nsh-core` feature | 生成文件数 | `nsh/index.d.ts` |
|---|---|---|
| 默认 | 13 | **不存在** |
| `declarations` | 18 | 存在，102 KB，40 个 `declare function` |

配置方式：应用 `tsconfig.json` 只写 `extends: "./.nsh/tsconfig.json"`，
编译选项全来自 nsh 生成的基线，nsh 升级时应用侧不用改。

**由此得出的工程约束**：类型生成必须与构建一起跑。`nsh` 的每个构建类子命令
都会刷新 `.nsh/types`，这正是官方设计——声明与产物同源，不会各走各的。

### 6.9 bundler 不做类型检查

`nsh-bundler` 只看语法。实测一个真实的漏改：删掉一段重复文案时连带删掉了
`serviceCount` 函数，构建正常、窗口正常打开，只有到渲染「服务 N/3」那一行
才抛异常，表现为计数恒为 0/3。

界面跑在 QuickJS 里，这类错误不会 stack trace 到终端，最难定位。

`nsh check` 已经覆盖这一步，且不需要 Node 环境：它自带 TypeScript 7
（Go 实现的单可执行文件），首次运行时从 npm 下载约 9 MB 并按记录的
checksum 校验，缓存在 `~/Library/Caches/nsh`。`--tsc` 或 `NSH_TSC`
可指定别的编译器。

所以「自带类型检查」不是我们额外搭的东西，是 nsh 的标准流程——这也说明
绕过 CLI 自建构建链的代价不止多写代码，还丢了一整套现成工具。

接上类型检查的当次即抓到一个遗留错误（`STATE_TEXT` 已被删除但仍被引用），
证明它不是形式主义。

### 6.11 真实画面进入窗口（M1a）

**结论**：真实 Android 画面（1920×1080）显示在本项目自己的 `NSWindow` 里，
随设备输入实时更新。这是「窗口归我们所有」这条约束第一次被端到端验证。

链路：

```
emulator → scrcpy-server（adb forward）→ 自研 client 解析
        → ffmpeg 解码 → BGRA 帧 → 最新帧槽位
        → 主线程定时器 → CALayer.contents → 我们的 NSView → 我们的 NSWindow
```

跨四个执行上下文：设备端 Java、socket 读线程、解码线程、主线程。
它们之间只通过一个「最新帧」槽位相连——不排队、不等待，因为视频只关心
现在该显示什么。

#### 纹理必须有 layer 才能上屏

纹理是像素容器，不是可显示对象。上传到 `MTLTexture` 之后，还需要一层把它
画到屏幕上——`CALayer.contents` 接一个 `CGImage`，并且视图要 `setWantsLayer(true)`
才有 backing layer 可放。

缺这一层的表现是：上传计数正常增长、日志一切正常、窗口全黑。
判断画面是否真的显示，可靠证据是看窗口，不是看上传计数。

#### 为什么不用 Metal 渲染管线

Metal 显示需要编译着色器、建渲染管线。M1a 要验证的是「帧能进我们的窗口」，
而管线是独立的、与窗口所有权无关的风险——混在一起，失败时无法归因。

代价是每帧一次 CPU 位图构造（1080p 约 1-2ms）。够用，但不理想；
换成 Metal 是性能工作，不是正确性工作。

#### 帧的驱动方式

由主线程定时器（16ms）驱动，不由界面驱动。界面的职责是布局，它不知道
帧的节奏；让界面驱动只能靠猜一个间隔，猜大了掉帧、猜小了空转。多个
定时器会互相错拍，表现为画面抖动。

回调签名必须写成 `(timer, info)` 两参。写成单参在多数 ABI 上"能跑"，
但那是未定义行为——多传的参数被静默丢弃，换个平台就崩。

### 6.12 对设计的影响（M0 后更新）

| 项 | 结论 |
|---|---|
| 界面语言 | TSX，已跑通真实窗口 |
| 宿主通道 | 复用 nsh 的 `HostChannel`，未自造传输 |
