# 工作区保护与版本启动

2026-11-20 在 Apple M4、16 GiB 内存、macOS 27.2.1 上运行签名的 release 应用。测试使用独立工作区、Android 用户目录和本机 ADB 服务，保留原有用户工作区。资源为 Emulator 37.2.13、Platform-Tools 37.0.1、Build-Tools 34.0.0、scrcpy-server 5.0.1 和 Google Play ARM64 镜像。

## 首次打开

| 输入与操作 | 检查结果 |
|---|---|
| 清除测试进程的 `WINDROID_HOME`，在临时家目录的 `.windroid` 中放一份笔记 | 启动窗口显示该目录的路径及缺少格式标记的原因。点「选择其他目录…」后取消，回到原提示。 |
| 在同一进程中选取实例缺少镜像修订的目录，再选择空目录 | 文件夹面板显示实例记录的路径及缺少的字段。关闭错误提示后可以继续选择。选择空目录后打开主窗口，所选位置生成 `workspace-format` 和注册表锁。再次启动并重选该工作区，格式标记的 inode 与修改时间均保持不变。 |
| 打开存储设置或迁移事务损坏、预放组件不完整、格式标记不可读的目录 | 启动窗口显示对应的路径和原因，可以退出或另选目录。退出后，目录快照与启动前一致。 |
| 现有注册表锁权限为 000 或 0400，或只读的 `instances` 目录中缺少锁 | 普通用户在启动窗口看到权限错误。目录快照确认未创建首屏标记或注册表锁。 |
| 预放官方 scrcpy-server 5.0.1，分别直接启动和从文件夹面板选入 | 确认框列出路径和资源。直接启动后取消会结束启动，从文件夹面板选入后取消则返回面板。两次取消后目录快照都保持原样。再次选择并确认后建立工作区，原组件目录及 JAR 保持完整。 |

在这台 Mac 上，单独运行 AppKit 文件夹面板时，点选列表行后目录属性保持原样，确认打开后系统为该目录新增 `com.apple.macl`。Windroid 在面板接受所选目录前完成检查和建库确认。实测拒绝或取消时，原目录和候选目录均未新增该属性。[文件夹面板校验](../../crates/host/src/surface/workspace.rs)

以下命令在普通 macOS 用户会话中运行。脚本在临时目录启动签名应用，操作真实窗口，对照目录成员、可读文件 SHA-256、权限、大小、inode、mtime、ctime 及可读扩展属性。权限夹具中的不可读文件以元数据核对。[原生窗口验收脚本](../../scripts/check-workspace-gate.py) · [目录与实例回归](../../crates/runtime/tests/workspace.rs) · [宿主权限回归](../../crates/host/src/library/tests.rs)

```sh
out="$PWD/build/workspace-selection"
bash scripts/package-macos.sh "$out"
python3 scripts/check-workspace-gate.py "$out/Windroid.app" \
  "$WINDROID_RELEASE_ARCHIVES/scrcpy-server-v5.0.1" "$out/evidence/gate"
```

## 真实客户机与窗口

同卷与跨卷各使用一个全新 v1 工作区。A、B 共用 API 34 r14，C 使用 API 33 r9。A 写入私有文件后保持开机，将组件和镜像迁到两个新目录。两次实测中，A 在迁移后和关机重开后均能读回原文件，B 的私有盘里没有该文件。单独将镜像迁回默认位置后，C 正常启动并回报 API 33。[真实迁移用例](../../crates/runtime/tests/real_emulator.rs)

同卷耗时 164.25 秒。跨卷在 `e7c8b55` 的 release 构建上通过指向独立 APFS 挂载点的符号链接选择目标卷。用例核对的源、目标设备号分别为 16777229 和 16777242，耗时 177.24 秒。

下列实机记录来自 `1a77eb9` 交付的资源布局和启动链。测试工作区预放了四个官方组件及 API 34 r14 镜像，原生提示列出五个版本。确认建库后创建「我的 Android」，重开后注册记录保留 API、标签、ABI 与修订 14。

- 在生产应用打开实例主屏和系统「设置」的独立应用窗口。两者都显示 Android 内容。关闭主屏后，在保留的应用窗口点击「Network & internet」，窗口显示网络子页，客户机回读的前台 Activity 为 `com.android.settings/.SubSettings`。主屏曾显示 Android 自身的 USB 调试授权框，本次操作未点击授权。
- 宿主 PATH 首项放置会留下调用标记的替身 adb，旧的工具与 SDK 路径变量也指向替身。官方 API 33 r9、34 r14 和 35 r9 客户机均能开机并回读系统服务，替身调用标记为空。API 35 在独立镜像目录初始化自己的用户盘。用例单独核对 Activity、Package 和 Window 三个服务。[真实客户机用例](../../crates/runtime/tests/real_emulator.rs)
- 实例已绑定 API 34 r14 后，在相同 API、标签及 ABI 下另放完整的 Google 历史镜像。历史归档文件名为 `34_r13.zip`，其中 `source.properties` 实际声明修订 8，按元数据将其放入 `r8/`。重开应用并启动原实例后，注册记录仍为修订 14，QEMU 的 `-sysdir` 指向 `r14/`。客户机回读系统构建号 `UE1A.230829.036.A4 / 12096271`，与 r14 的 `build.prop` 一致。相邻旧镜像为 `UE1A.230829.036.A2 / 11596452`。本次旧包 SHA-256 为 `2716ea6bb6cf9a6fbd9ce8799425e25413ac8a82652858a0c82556921127753a`。受支持的可安装版本仍由发布清单列出。[Google 历史镜像归档](https://dl.google.com/android/repository/sys-img/google_apis_playstore/arm64-v8a-34_r13.zip)
- 在两个修订并存的真实实例上，另用显式 ADB 和 JAR 运行流协议验收，读到主屏 864 × 1920、独立应用屏 720 × 1280。两个会话均解出非黑 BGRA 帧。关闭主屏后向应用屏发送方向键，收到后续非黑帧。[流协议实机用例](../../crates/stream/tests/real_stream.rs)
- 在 A 的私有盘写入测试文件，关机时保留 Quick Boot 快照。B 看不到该文件。重开注册表并恢复 A 后，文件内容和 Android 的 `boot_count` 均与停止前相同。
- 在专用工作区中强制结束桌面宿主，保留其 QEMU 子进程。通过 `lsof` 在该进程查到四个组件和一个镜像的共享目录描述符。独立进程尝试对 Platform-Tools 版本目录取得非阻塞排他锁，在 QEMU 存活时失败，QEMU 退出后立即成功。[启动时继承版本使用权](../../crates/runtime/src/instances/process.rs)

运行以下用例时，`WINDROID_TEST_RESOURCES` 指向包含 `runtime`、`system-images` 的官方展开资源父目录，`WINDROID_TEST_API33_ZIP` 指向完整 API 33 r9 官方 ZIP。`WINDROID_TEST_MIGRATION_VOLUME` 可指向独立挂载的可写卷，测试会核对两个文件系统的设备号。用例自行创建私有工作区，并为独立 ADB 服务关闭对其他模拟器端口的自动扫描。

```sh
cargo test --locked --release -p runtime --test real_emulator -- \
  --ignored --nocapture --test-threads=1
```

四个组件和镜像的同长度损坏、下载暂停、断卷、重装与 ZIP 导入另有逐项验收。设置与引导文档分别标明原生窗口操作和受控回执的覆盖范围。[版本资源核验与目标卷传输](05-版本资源核验与目标卷传输.md) · [设置与引导](04-呈现域.md)
