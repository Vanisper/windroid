## 两个工作区使用同一资源根与父子根（2026-11-20）

Apple M4、macOS 27.2.1，APFS 工作卷。每组使用两个新工作区、固定 console 5570 与 5572、隔离的 Android 用户目录和本地 ADB 服务。通过生产存储接口逐个预览两个根，完整核验后各自确认使用；第一个工作区在第二个工作区选目录之前已经创建实例。随后重读两边的实例记录，启动真实的 Emulator 37.2.13 与 Android 14 Google Play ARM64 r14。

- **同一根。** 将四种组件版本与 `android-34/` 放入同一个目录。两个工作区的组件和镜像都选择此根，所有版本原地复用。
- **父子根。** 父目录与其 `more-versions/` 子目录各放一套官方版本。工作区 A 的组件在父目录、镜像在子目录。工作区 B 的组件在子目录、镜像在父目录。两种布局都分别测 A 先接入和 B 先接入。先接入的一方先选镜像再选组件，另一方先选组件再选镜像。

| 资源根 | 工作区接入次序 | A 冷启动至就绪 | B 冷启动至就绪 |
|---|---|---:|---:|
| 同一根 | A → B | 84.91 秒 | 72.78 秒 |
| 同一根 | B → A | 25.31 秒 | 164.34 秒 |
| 父子根 | A → B | 39.49 秒 | 30.25 秒 |
| 父子根 | B → A | 23.16 秒 | 30.54 秒 |

八次启动均通过 Android 开机、Activity、Package、Window 服务和目标设备 AVD 名检查。每组先让 A 在客户机私有路径写入 `A`，再保持 A 运行并启动 B。B 首次读取该路径时文件不存在。B 写入 `B` 后，分别通过实例绑定的 ADB 回读 `A` 与 `B`。每次还核对会话实际使用的组件、镜像根以及私有 `config.ini` 中精确到 `r14/` 的 `image.sysdir.1`。每组最后正常关闭两台设备。

**复验。** 将 `WINDROID_TEST_RESOURCES` 设为包含同卷官方 `runtime/` 与 `system-images/android-34/` 的目录，保持 5570–5573 空闲后执行下列命令。用例在独占临时目录中克隆所需包。隔离的 ADB 服务设定 `ADB_LOCAL_TRANSPORT_MAX_PORT=5553`，由两台模拟器主动登记；这可防止该验收服务自动连接其他会话的模拟器。此组覆盖同卷文件系统和实际运行后端。原生文件面板和跨卷传输分别有独立实测。[双工作区用例](../../crates/runtime/tests/shared_versioned_roots.rs) · [原生呈现实测](04-呈现域.md) · [目标卷传输实测](05-版本资源核验与目标卷传输.md)

## 版本目录的只读接入与跨卷迁回（2026-11-20）

**真实只读卷。** 在 Apple 芯片 Mac 上，将含四项官方运行组件的独立 APFS 磁盘映像以只读方式挂载。源设置指向一个未挂载的卷，目标文件夹使用自定义名称。原生存储接口逐文件核验 Emulator、Platform-Tools、Build-Tools 和 scrcpy-server，预览显示四个版本可直接复用、复制空间为零。确认后重读工作区设置，组件根已切换。准备该卷时，首次使用的复制工具遗漏了 Emulator 清单中的四个 `._` 文件，核验指出具体缺失路径；补齐后通过。[只读卷用例](../../crates/runtime/src/storage/tests.rs)

**真实可写卷。** 在另一独立 APFS 卷上，目标已有完整 Platform-Tools 和空的 scrcpy 版本目录。源与目标的 Platform-Tools 通过全量核验，预览只需复制一个 733,930 字节的官方 JAR，估算额外空间 749,568 字节，发布后的 JAR 实际分配 737,280 字节。源副本默认保留。迁回前故意改动默认位置 JAR 的一个字节并恢复修改时间，预览报告冲突，确认失败后两侧原样保留。还原内容再预览，迁回额外空间为零。显式勾选清理后，另一读者占用的源 JAR 被保留，释放租约并重开后才完成清理。[跨卷迁回用例](../../crates/runtime/src/storage/tests.rs)

**真实卸载。** 为未来下载选择手工挂载点下的空目录后，卸载磁盘映像，并在同一位置保留宿主卷上的空文件夹。重新读取设置后，运行时报告所选卷离线，宿主磁盘上没有生成版本或暂存目录。[挂载生命周期用例](../../crates/runtime/src/storage/tests.rs)

**中断与恢复夹具。** 使用官方 scrcpy JAR，在临时目录构造五种事务现场，分别重开两次。复制中断和发布后尚未切换时，工作区沿用原根并还原目标空目录。设置已提交时沿用新根；已同意清理的旧文件若有同大小改动，即使恢复原修改时间也会保留，并在设置中列出原因。源目录暂时移开后会保留清理记录，接回并复核后完成清理。另有独立的双进程测试覆盖旧对象、改名后的新对象和同一镜像的不同修订。[事务检查点](../../crates/runtime/src/storage/transaction.rs) · [跨进程版本锁](../../crates/runtime/src/storage/tests.rs)

## 1. AVD 可以手工创建,不需要 avdmanager

**问题**：能否不依赖 cmdline-tools + JDK 生成实例？

**方法**：手写 `<name>.ini` + `<name>.avd/config.ini`（约 20 行）,不经过 avdmanager,直接启动。

**结果**（实测）：启动成功,25 秒完成引导,1280×720 / 240dpi。

**踩坑**：`hw.cpu.arch` 必须写 `arm64`。写 `aarch64` 时模拟器直接 FATAL：

```
FATAL | CPU Architecture 'aarch64' is not supported by the QEMU2 emulator
```

**影响**：AVD 生成采用手写配置方案,省去 300 MB 依赖（JDK + cmdline-tools）,且模板可做单元测试。

## 2. 多实例共享同一份镜像,数据完全隔离

**问题**：多实例是否必须各存一份 3.1 GB 镜像？

**方法**：两个自建 AVD 的 `image.sysdir.1` 指向同一镜像目录,同时启动。

**结果**（实测）：

```
BOTH BOOTED at 36s
devices: emulator-5590, emulator-5592
A 写 /sdcard/probeA → B 看不见（数据隔离）
镜像目录 mtime 未变（只读共享）
```

**影响**：镜像按 apiLevel/tag/abi 存一份,实例只增加自己的 userdata。多实例的存储成本可接受。

## 3. 端口范围是硬约束,上限 16 组

**问题**：多实例能开多少个？

**结果**（实测 + 官方文档）：

```
WARNING | Requested adb port (5591) is outside the recommended range [5555,5586]
```

官方 `-help-port` 说明：console 端口必须是 5554–5584 的偶数,且 `<port>+1` 也必须空闲,任一被占用则模拟器启动失败。

**影响**：设计端口分配器,范围 5554–5584 步进 2,共 16 组；达到上限时拒绝创建并给出替代动作。

## 4. adb 是单 server 多设备模型

**问题**：一个实例是否启动一个 adb？

**结果**（实测）：

```
$ lsof -nP -iTCP:5037
adb  19730  TCP 127.0.0.1:5037 (LISTEN)      ← 只有一个

$ pgrep -fl adb

## 5. data 分区与镜像无关

**问题**：data 分区大小是否影响镜像本身？

**方法**：配置 2G 启动,检查 guest 与 host 两侧。

**结果**（实测）：

```

**影响**：data 分区只是实例私有的可写数据盘,镜像完全只读共享。

## 6. 6 GiB 下限的确切来源

**问题**：为什么配置 1G/4G/5G 都会被抬到同一个值？

**方法**：逐个测试 1G/4G/5G/6G/8G/16G,并阅读模拟器源码。

**结果**（实测 + 源码）：

| 请求值 | 模拟器改写后的值 | guest 可见 |
|---|---|---|
| 1G / 4G / 5G | 6442450944（6 GiB） | 5.8G |
| 6G / 8G / 16G | 原值保留 | 5.8G / 7.7G / 15G |
| 不写该键 | 6442450944 | 5.8G |
| `-partition-size 1024` | 6442450944 | 5.8G |

源码位于 `platform/external/qemu/android-qemu2-glue/main.cpp`：

```cpp
// studio avd manager does not allow user to change partition size, set a
// lower limit to 6GB.
constexpr auto kMinPlaystoreImageSize = 6LL * 1024 * 1024 * 1024;
const int myApiLevel = avd ? avdInfo_getApiLevel(avd) : 1000;
if (myApiLevel >= 24 || fc::isEnabled(fc::PlayStoreImage)) {
    if (firstTimeSetup && hw->disk_dataPartition_size < kMinPlaystoreImageSize) {
        hw->disk_dataPartition_size = kMinPlaystoreImageSize;
        avdInfo_replaceDataPartitionSizeInConfigIni(..., kMinPlaystoreImageSize);
    }
}
```

6 × 1024³ = 6442450944,与实测被写入的十进制值一致。

**跨版本验证**（实测,由子代理完成）：

| 模拟器版本 | API 23 | API 24+ |
|---|---|---|
| 33.1.24 | 1G 保持 1G | 抬到 6 GiB |
| 35.2.10 | — | 抬到 6 GiB |
| 37.2.13 | 1G 保持 1G | 抬到 6 GiB |

API 24 是精确阈值,跨模拟器版本稳定。该 API 守卫是 emu-31-release 引入的；常量数值自 emu-29.0-release 起未变。

**影响**：下限写进设计（6 GiB）,但仍保留运行时回读,因为常量可能随模拟器版本变化。

## 7. 改分区大小会清空数据,且 API 33+ 完全无效

**问题**：创建后能否放大 data 分区？数据会保留吗？

**方法**：分三个对照实验,每组都写标记文件后重启验证。

**结果**（实测）：

| 场景 | 结果 |
|---|---|
| 只重启,不改大小 | 标记文件完好 |
| API 30：6G → 16G → 20G → 24G | **每次扩容都生效,/data 变大,但所有文件消失**,用量回到 33M |
| API 34：6G → 16G | **/data 仍是 5.8G**,resize 日志 0 条 |

API 30 的 resize 日志（证明扩容确实执行了）：

```
WARNING | userdata partition is resized from 6144 M to 16384 M
WARNING | userdata partition is resized from 16384 M to 20480 M
WARNING | userdata partition is resized from 20480 M to 24576 M
```

API 33+ 无效的原因（源码）：该版本 userdata 使用 qcow2,而 resize 逻辑要求 `pathIsExt4`：

```cpp
} else if (!hw->hw_arc) {
    if (System::get()->pathIsExt4(hw->disk_dataPartition_path) && ...
```

API 34 实例的 `userdata-qemu.img` 实测为 `QEMU QCOW2 Image (v3)`,`pathIsExt4` 返回 false,整段逻辑被跳过。

**影响**：不提供「改分区大小」功能。创建时一次定死。

## 8. 单实例 CPU、内存与多实例并发

本节实测使用 10 核、16 GiB 的 Apple M4，Emulator 37.2.13（build 16740729），Android 14 Google Play ARM64 镜像。上游源码链接固定到同系列公开稳定版 37.2.12。对 37.2.13 的判断分别标明虚拟机回读、启动参数和二进制核验。内存统一用 MiB、GiB，1 GiB = 1024 MiB。[上游版本提交](https://android.googlesource.com/platform/external/qemu/+/8aaadeb1fea1202b287f1b8361f764a98950a27e)

### 8.1 单实例 vCPU 与并发分配

**复验方法。** 每个 AVD 使用独立的临时 `ANDROID_AVD_HOME`、`ANDROID_USER_HOME`、console 端口和 QMP socket，共享只读镜像。按第 1 节生成 `test.avd/config.ini`，设置 `hw.cpu.ncore` 为待测值、`hw.ramSize=2560`。两台并发测试分别取 5660、5662 端口。以下命令在 VM 创建后暂停客户机，避免把 Android 开机耗时计入分配结果。

```sh
emulator -avd test -port "$port" -no-window -no-snapshot -no-audio \
  -no-boot-anim -no-metrics -gpu host -feature -Wifi \
  -qemu -S -qmp "unix:$qmp_socket,server,nowait"
```

连接 QMP socket，收到问候后依次发送 `{"execute":"qmp_capabilities"}`、`{"execute":"query-cpus-fast"}`、`{"execute":"query-status"}`。第二条返回数组的长度是已创建的 vCPU 数量。并发测试保留第一个进程，测完第二个后再向两者发送 `{"execute":"quit"}`。

| 输入 | 37.2.13 实测 |
|---|---|
| 1 核、8 核，分别启动 | QMP 分别返回 1、8 个 vCPU，VM 状态为 `prelaunch` |
| 9 核 | QEMU 在机型初始化时拒绝，日志为 `Number of SMP CPUs requested (9) exceeds max CPUs supported by machine 'mach-virt' (8)` |
| 两个 AVD 各 6 核 | 两个进程同时存活，QMP 分别返回 6 个 vCPU，合计超过宿主的 10 个逻辑核。此测试未运行 Android 工作负载 |

Apple Hypervisor 将每个 vCPU 映射为一个宿主线程。上表测量虚拟机能否创建这些线程。要比较超配对桌面响应的影响，还需让两个 Android 实例同时执行相同的前台工作负载，比较输入延迟或帧时间。现有数据不能给出性能开始下降的核数比例。[Apple Hypervisor 的虚拟资源映射](https://developer.apple.com/documentation/hypervisor#Virtual-Resource-Mapping)

**源码。** QEMU2 的 `-cores` 参数解析器接受 1–64。进入 ARM `virt` 机型后，GICv2 路径另受 `GIC_NCPU=8` 限制。GICv3 则根据中断控制器的地址映射计算上限。8 核结论适用于这里验证的机型和中断控制器。另在本机调用 `hv_vm_get_max_vcpu_count` 返回 64，两个原生 HVF 进程也各自成功创建 6 个 vCPU。[参数解析](https://android.googlesource.com/platform/external/qemu/+/8aaadeb1fea1202b287f1b8361f764a98950a27e/android/android-emu/android/main-common.c#2157) · [机型检查](https://android.googlesource.com/platform/external/qemu/+/8aaadeb1fea1202b287f1b8361f764a98950a27e/hw/arm/virt.c#1367) · [GIC 常量](https://android.googlesource.com/platform/external/qemu/+/8aaadeb1fea1202b287f1b8361f764a98950a27e/include/hw/intc/arm_gic_common.h#32) · [Apple Hypervisor API](https://developer.apple.com/documentation/hypervisor/hv_vm_get_max_vcpu_count(_:))

### 8.2 客户机内存下限

**源码。** 模拟器在 `android/android-emu/android/main-common.c` 中按 API、屏幕像素和 AVD 类型确定最低内存，再将过低的配置抬到该值。以下为普通 64 位 Google Play 镜像在 Windroid 所涉及版本的规则。像素数取 `hw.lcd.width × hw.lcd.height`。源码还按 AVD 类型为 Android TV、Wear、XR 单独指定 1、2、4 GiB。给普通 Google Play 镜像选「4K 电视」显示模板，仍按该镜像和屏幕像素计算。[内存规则与分支顺序](https://android.googlesource.com/platform/external/qemu/+/8aaadeb1fea1202b287f1b8361f764a98950a27e/android/android-emu/android/main-common.c#1266) · [API 37 调整的原始变更](https://android.googlesource.com/platform/external/qemu/+/d76e6c2450f8d146cdcb6c34da9d675ee133afc9)

| 普通镜像 | 非折叠、少于 300 万像素 | 折叠或至少 300 万像素 |
|---|---:|---:|
| API 29–32 | 2 GiB | 2 GiB |
| API 33 | 2 GiB | 4 GiB |
| API 34–36 | 2.5 GiB | 4 GiB |
| API 37 起（按该版本规则） | 4 GiB | 4 GiB |

**如何取得输入。** 常规 AVD 由根配置中的 `target` 给出 API，模拟器再从镜像 `build.prop` 的产品属性识别 AVD 类型。主屏像素取最终生效的宽高，折叠条件取模拟器识别的折叠区域、铰链或卷屏配置。显示模板的名称和下载文件名都不能确定这些值。选定镜像后更换显示模板，要按新配置重新计算。Windroid 可随受管 Emulator 版本校验同一套规则，发布或升级时用下表两个临界配置和已支持的镜像类型对照启动参数。[常规 AVD 的加载顺序](https://android.googlesource.com/platform/external/qemu/+/8aaadeb1fea1202b287f1b8361f764a98950a27e/android/emu/avd/src/android/avd/info.c#1060) · [镜像产品属性与 AVD 类型](https://android.googlesource.com/platform/external/qemu/+/8aaadeb1fea1202b287f1b8361f764a98950a27e/android/emu/avd/src/android/avd/util.c#236)

**实测。** 此前在 API 34 手机上设置 `hw.ramSize=1536`，启动日志显示 `Increasing RAM size to 2560MB`。边界复验用同一镜像，分别修改 `hw.lcd.width`、`hw.lcd.height` 和 `hw.ramSize`。对独立临时 AVD 运行下列预检命令，在 `Concatenated QEMU options` 中读取 `-m`。最后一个参数有意让 QEMU 在解析阶段退出，因此表中结果只说明将分给客户机的容量，未测宿主常驻内存或完整开机。

```sh
emulator -avd probe -no-window -no-snapshot -no-audio -read-only -verbose \
  -qemu -windroid-probe-invalid
```

| 像素尺寸 | 配置内存 | 交给 QEMU 的内存 |
|---|---:|---:|
| 1999 × 1500（2,998,500 像素） | 512 MiB | 2560 MiB |
| 2000 × 1500（3,000,000 像素） | 512 MiB | 4096 MiB |
| 3840 × 2160 | 512 MiB | 4096 MiB |
| 1080 × 2400 | 9216、17408 MiB，分别预检 | 9216、17408 MiB |

### 8.3 单实例内存上限与宿主预算

**机型上限（源码、二进制核验）。** Apple Silicon 版 ARM `virt` 的内存映射定义 `RAMLIMIT_GB=31`，机型初始化时超过 31 GiB 即退出。本机 37.2.13 的 `qemu-system-aarch64-headless` 中，`_machvirt_init` 在该错误分支将十进制 31 传给 `mach-virt: cannot model more than %dGB RAM`。可用 `xcrun llvm-objdump --disassemble-symbols=_machvirt_init` 对该二进制复验。Google 命令行手册给 `-memory` 标注 1536–8192 MB。Windroid 通过 AVD 的 `hw.ramSize` 配置客机，8.2 的预检验证了这条路径能传入超过 8 GiB 的值。[上限定义](https://android.googlesource.com/platform/external/qemu/+/8aaadeb1fea1202b287f1b8361f764a98950a27e/hw/arm/virt.c#125) · [机型拒绝条件](https://android.googlesource.com/platform/external/qemu/+/8aaadeb1fea1202b287f1b8361f764a98950a27e/hw/arm/virt.c#1385) · [Android Emulator 命令行手册](https://developer.android.com/studio/run/emulator-commandline#common)

**宿主兼容性。** 普通手机镜像的宿主 CPU 最低 2 核、建议 4 核。API 37 起的宿主总内存最低 4 GiB、建议 16 GiB。模拟器启动时另行检查这些宿主条件。[宿主 CPU 检查](https://android.googlesource.com/platform/external/qemu/+/8aaadeb1fea1202b287f1b8361f764a98950a27e/android/emu/check/src/android/system_check.cpp#62) · [宿主内存检查](https://android.googlesource.com/platform/external/qemu/+/8aaadeb1fea1202b287f1b8361f764a98950a27e/android/emu/check/src/android/system_check.cpp#91)

**共享预算的来源。** 在一台 8 GB Mac 上，UTM 作者为运行 PixelOS 与 GApps 的虚拟机分配 6 GiB 时观察到大量换页和启动冻结，据此建议单台 VM 最多使用半数物理内存。Windroid 将 50% 选为所有活动实例的共享预算。现有 Rust 宿主另设 3 台上限，两项都是产品策略。原始规格及该观察均未给出跨机型并发基准。[UTM 作者的实机记录](https://kywk.github.io/moco/utilities/android/utm-android-vm/03-arm64-方案：pixelos-gsi-虛擬機/) · [预算的初始定义，第 3.2 节](https://github.com/Vanisper/windroid/blob/223ef9ba553f8d641f1aeec1763a0c06faf3ed2d/docs/产品与架构设计.md#L42-L54) · [宿主实现](../../crates/host/src/library/commands.rs)

**验证范围。** 第 2 节测了两个实例同时开机和数据隔离，第 8.1 节测了两个暂停的 VM 各自分配 6 vCPU。项目尚无 50% 两侧的内存压力对照，或三台与四台相同负载的启动峰值、换页和交互延迟对照。设计保留 50% 作为共享预算上限，按启动时可用资源决定台数。跨内存容量、后台负载和图形配置的安全余量仍待标定。[产品设计中的资源检查](../产品/01-产品形态与交互.md#六资源治理)

macOS 的 Dispatch 内存压力事件提供正常、警告和严重三个等级。它们本身没有给出可再分配的字节数。设计稿中的“当前预计可用”是独立的宿主观测示例值。生产实现需要用启动时的内存峰值、换页与宿主响应数据标定估算方法。[Apple 内存压力事件](https://developer.apple.com/documentation/dispatch/dispatch_source_memorypressure_flags_t)

## 10. 镜像对 AVD 的最小要求

**结果**（实测）：AVD 只通过一个键引用镜像——`image.sysdir.1`。该目录至少需要 `system.img`、`vendor.img`、`kernel-ranchu`、`ramdisk.img`,其余可缺省。

**影响**：镜像目录的内部布局是我们的契约,不是 Google 的。接入 AOSP 或 LineageOS 构建产物时,AVD 生成逻辑无需改动,只需产出符合该布局的目录。

## 11. 模拟器与镜像的版本耦合是声明式

**结果**（实测）：镜像的 `source.properties` 包含：

```
Pkg.Dependencies=emulator#34.2.16
Pkg.Revision=14
AndroidVersion.ApiLevel=34
SystemImage.TagId=google_apis_playstore
```

本机模拟器 37.2.13 运行该镜像正常,说明这是**最低版本要求**,不是精确匹配。

**推断（未实测）**：模拟器低于该声明值时大概率拒绝启动。未做验证,因为需要安装旧版模拟器,成本高且对设计无影响——设计上只需启动前校验并标记不可用。

## 模拟器图形后端与 CPU

无窗口模式仍然需要图形渲染：Android 的应用与系统合成照常执行，只是没有
模拟器自身的框架窗口。`hw.gpu.enabled=no` 或自动选择软件后端时，1080p
合成由 SwiftShader 在 CPU 上执行。

本机 Apple M4、tv14、1920×1080 的实测：

| 启动参数 | 实际渲染器 | 启动后高负载阶段的 qemu 占用 |
|---|---|---|
| 未指定 `-gpu` | SwiftShader Device (LLVM 10.0.0) | 约 700%–750% |
| `-gpu host` | Apple M4 | 同一阶段约 75%–370%，随后继续回落 |

本次探针对照时使用 `WINDROID_GPU` 切换 `-gpu` 参数。当前 macOS 客户端启动时传入产品默认的 `-gpu host`。[模拟器启动参数](../../crates/runtime/src/instances/process.rs) · [运行时组件设计](../架构/01-运行环境域.md)

判断依据必须同时包含宿主机与客户机：客户机 `top` 可能显示大部分虚拟核
空闲，而宿主机 qemu 仍因软件图形栈高占用。只看其中一侧会得到相反结论。
