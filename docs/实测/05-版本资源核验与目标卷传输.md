# 版本资源核验与目标卷传输

2026-11-20 在 Apple 芯片 Mac 上，以七个固定发布档案、全新工作区和独立挂载的磁盘映像验收。真实归档包含 607 个文件和 113 个子目录。Emulator 的启动程序和两个 QEMU 文件均含 arm64，Platform-Tools 的 adb、Build-Tools 的 aapt 均为含 arm64 与 x86_64 的 universal 可执行文件。

## 官方档案与清单重建

Google ZIP 先按官方仓库记录验证长度和 SHA-1，scrcpy-server 按发布者的 SHA-256 验证。同一次重建再读取每个 ZIP 条目的相对路径、类型、原始长度、执行位及内容 SHA-256，并补齐隐含的父目录。单文件服务器在版本目录内固定为 `scrcpy-server.jar`。以相对路径字节序排列的 TSV 是跨卷版本摘要的输入。[Android 官方组件](https://dl.google.com/android/repository/repository2-3.xml) · [Google Play 镜像](https://dl.google.com/android/repository/sys-img/google_apis_playstore/sys-img2-3.xml) · [scrcpy-server 发布校验和](https://github.com/Genymobile/scrcpy/releases/download/v5.0.1/SHA256SUMS.txt)

| 版本 | 普通文件 | 子目录 | 展开字节 |
|---|---:|---:|---:|
| Emulator 37.2.13 | 354 | 49 | 1,309,741,043 |
| Platform-Tools 37.0.1 | 12 | 1 | 38,814,256 |
| Build-Tools 34.0.0 | 170 | 27 | 196,201,746 |
| scrcpy-server 5.0.1 | 1 | 0 | 733,930 |
| Android 13 · Google Play ARM64 r9 | 18 | 9 | 3,536,280,695 |
| Android 14 · Google Play ARM64 r14 | 23 | 12 | 3,341,086,447 |
| Android 15 · Google Play ARM64 r9 | 29 | 15 | 2,308,619,205 |

将 [catalog.rs](../../crates/runtime/src/provision/catalog.rs) 指定的七个原始文件按 URL 原名放入同一目录。在仓库根运行以下命令，第二行指定用于对比的独立输出目录。本次 release 重建耗时 34.46 秒，七份结果均与随应用交付的文件逐字节一致。

```sh
WINDROID_RELEASE_ARCHIVES=/path/to/official-archives \
WINDROID_MANIFEST_OUTPUT=/path/to/rebuilt-manifests \
cargo test --release -p runtime --lib rebuild_release_manifests -- --ignored

diff -qr crates/runtime/src/provision/manifests /path/to/rebuilt-manifests
```

首次接入和显式完整核验读取整个版本。日常检查核对清单内的文件类型、大小、必要执行位、包元数据和宿主程序架构，比较本机文件变更信息；只有上次完整验过的内容可使用快速结果。缺乏细粒度变更时间的卷会重做完整核验。本机变更信息用于使工作区缓存失效，跨卷比对使用清单的内容摘要。[核验实现](../../crates/runtime/src/provision/manifest.rs)

## 真实下载、重新安装与 ZIP 导入

在独立 12 GiB APFS 卷下载四个组件，单独同意下载 API 34 r14。两次验收分别保留 7,110,647 和 11,763,632 字节前缀后手动暂停。重新打开工作区能读回这个前缀，切换到另一镜像根后显示零字节，选回原根后继续、完成核验并安装。在另一个全新工作区接入同一资源根，原位读取成功。

在上述版本的 `emulator`、`adb`、`aapt`、`scrcpy-server.jar`、`system.img` 中各改一个字节，保留长度、执行位和原修改时间。每次重查均发现对应版本损坏，普通准备保持原目录对象，逐项确认后从官方源重新下载安装。五个新版本目录各自产生新的 inode，发布后逐文件复查通过。两轮验收分别运行 126.65 秒和 224.84 秒。[联网修复验收](../../crates/runtime/tests/versioned_packages.rs)

从系统卷读取 API 34 r14、API 35 r9、API 33 r9 三个完整官方 ZIP，在另一块 14 GiB APFS 卷按顺序预览、确认导入、验证发布并重新打开。三个实际目标均在该卷的镜像根下，各自以 `r14` 或 `r9` 结尾，三个版本可同时使用。本次耗时 64.96 秒。[三镜像导入验收](../../crates/runtime/tests/provision.rs)

## 目标卷故障与只读接入

- 在下载真实 API 35 官方镜像期间强制弹出专用 7 GiB APFS 磁盘映像。两次验收均得到系统 I/O 错误，挂载点没有在系统卷被重新创建；产品提示重新挂载后手动继续。重连后分别读回 6,455,158 和 11,337,612 字节前缀，手动继续均成功安装，耗时 48.69 秒与 92.41 秒。[强制弹盘验收](../../crates/runtime/tests/versioned_packages.rs)
- 在 64 MiB HFS+ 卷选择未来组件位置。启动下载前测得可用 65,499,136 字节，Emulator 所需 1,730,048,566 字节，返回空间不足，目标目录仍不存在。估算含剩余归档、展开副本及 4 MiB 临时开销。[小卷验收](../../crates/runtime/tests/versioned_packages.rs)
- 在该 HFS+ 卷预放官方 JAR 版本目录后，以只读方式重新挂载。从系统卷上的新工作区接入，JAR 完整核验通过，显示目标不可写，版本目录对象保持一致，同级没有新增文件。[只读卷验收](../../crates/runtime/tests/versioned_packages.rs)

## 同路径换卷与原卷发布恢复

在两份独立的 APFS 磁盘映像 A、B 上，分别改动官方 scrcpy-server 5.0.1 JAR 的一个字节，保留同一路径、文件长度和各自的 32,768 字节续传前缀。在 A 上取得修复确认后卸载 A，将 B 挂到相同路径。B 的该版本同样被识别为损坏，两个版本目录的 inode 均为 18。提交 A 的旧确认立即收到重新确认提示。比较 B 组件根下全部七项，路径、inode、权限、修改时间、状态变更时间与各文件的 SHA-256 均保持原值。[真实换卷测试](../../crates/runtime/tests/versioned_packages/volume_repair.rs)

另在 A 上预放 416,113,219 字节的官方 Emulator 37.2.13 ZIP，通过正常修复入口安装。在发布日志已落盘、原目录已进入备份、新目录已换入后，用 SIGKILL 终止安装子进程。卸载 A，将 B 挂到另一位置，再把 A 挂回原路径。第二轮实测设备号从 16777244 变为 16777246，发布记录内容与恢复确认令牌均保持一致。用重挂前的令牌恢复后，备份和日志已回收，独立的全量核验再次通过。两轮实际安装和换卷分别用时 11.52 秒与 12.56 秒。[真实发布中断测试](../../crates/runtime/tests/versioned_packages/volume_repair.rs)

2026-11-21 使用 `windroid-package-install-v1` 重跑同一用例，耗时 10.54 秒。换卷后 B 的七项内容与元数据保持原样，A 重挂后的设备号由 16777242 变为 16777246，恢复的 Emulator 37.2.13 通过完整核验。

复核时将 `WINDROID_QA_ROOT` 指向专用空目录、`WINDROID_QA_ARCHIVES` 指向存有固定版 Emulator ZIP 和 scrcpy-server JAR 的目录。

```sh
cargo test --release --locked -p runtime --test versioned_packages \
  replacement_rejects_old_confirmation_and_original_volume_recovers -- --ignored --nocapture
```

## 受控边界

本地 HTTP 服务分别复现服务器支持 Range、忽略 Range、请求中断与暂停，断言请求起点和最终字节。候选镜像下载保留当前绑定行，重开后仅在再次选中同一目标时续用前缀。发布事务用小型版本目录重建三个中断点，分别覆盖写完事务记录、移走原版本、换入新版本，重入后逐文件验收，备份和事务记录均被回收。另在换入后破坏暂存副本，分别覆盖有原版本备份、首次安装无备份两种情况，确认后均可重试。含未知文件的安装目录保留原样。这些检查使用固定测试数据；上述跨卷下载、弹出、重新安装和导入使用真实发布包。[受控测试](../../crates/runtime/src/provision/tests.rs)

## 会话期间更换 ADB 服务

在独立回环端口用内存服务返回协议 40。直接运行固定 Platform-Tools 37.0.1 的 `adb devices`，线上顺序为 `host:version`、`host:kill`；测试在收到第二条请求后立即终止客户端。改由 Windroid 的启动检查、设备枚举、设备 shell 分别访问同一受控端点，只收到三次 `host:version`，三种调用均报告协议 40 与 41 不兼容。[官方工具与受控服务测试](../../crates/adb/tests/command.rs)

流域夹具先返回 41，使会话建立检查、设备目录创建、JAR 推送和 forward 成功，随后改成 40。长连接启动、forward 清理和远端目录清理各自握手后返回，替换后的服务没有收到设备命令。该段使用脚本工具记录子命令；端点检查走本机 TCP。[会话中途替换测试](../../crates/stream/tests/protocol.rs)

子进程 PATH 只保留 macOS 系统目录后，用 Emulator 37.2.13、Platform-Tools 37.0.1 和 API 34 官方镜像启动两台私有 AVD。A、B 均完成冷启动，B 无法读取 A 写入的文件。A 再次启动时恢复 Quick Boot，`boot_count` 保持原值，私有文件可读，三次会话均正常停机。[真实双实例验收](../../crates/runtime/tests/real_emulator.rs)
