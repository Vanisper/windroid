# 设备域实测记录

支撑「设备域」设计决定的实测证据。对应设计文档：[架构/02-设备域](../架构/02-设备域.md)。

环境：macOS 27.2.1 / Apple M4；adb 1.0.41；emulator 37.2.13；镜像 android-30 default/arm64-v8a、android-34 google_apis_playstore/arm64-v8a。全部为手工构造 AVD（不用 avdmanager），`-no-snapshot` 冷启动。

---

## 1. 启动就绪的精确时序

**问题**：`sys.boot_completed=1` 是否代表可用？有没有更早或更可靠的就绪信号？

**方法**：100ms 轮询,同时记录 `adb devices -l` 状态、`pm list packages` 返回码、`sys.boot_completed`。

**结果**（android-30 冷启动）：

| 时刻 | 事件 |
|---|---|
| 0.57s | `adb devices -l` 显示 `emulator-5580 offline transport_id:59` |
| 9.50s | 转为 `device` |
| 9.77s | `pm list packages` → **rc=20**,stderr `cmd: Can't find service: package` |
| 10.24s | `pm list packages` → **rc=0**,163 行 |
| 11.18s | `sys.boot_completed` → 1 |
| 11.61s | `dumpsys package android`（220KB）耗时 0.070s,无阻塞 |

**关键结论**：**pm 比 boot_completed 早约 1.5 秒就绪**。`boot_completed=1` 时 pm 必然可用（时间差为负，不是滞后）。

**影响**：
- `adb wait-for-device` 不能作为就绪判据（9.5s 返回,pm 到 10.24s 才可用）
- `Ready` 状态用 `bootCompleted` 作门限（保守但稳定）,用 `pmReady` 提前预热应用清单

### 相关属性

`dev.bootcomplete` 与 `sys.boot_completed` 在**同一采样窗口翻转**（50ms 间隔连续采样,11.079/11.207/11.357 均为空,11.480 同时为 1）,无法用它们区分更早就绪。

`init.svc.bootanim` 在 `-no-boot-anim` 配置下从第一次可读起就是 `stopped`,不含信息量。

### adb 无 booted 类状态

`adb help` 原文：`wait-for[-TRANSPORT]-STATE` 支持 device / recovery / rescue / sideload / bootloader / disconnect,**没有 booted**。

offline 期间 `adb shell` 返回 rc=1 + `adb: device offline`。

## 2. 包列表输出格式

**结果**（实测,od 逐字节确认）：

```
pm list packages -3  →  package:com.probe.testapp\n   （无前缀、无空格）
pm list packages -s  →  同格式
```

android-30 实测计数：`-s` = 163,`-3` = 1（装测试包后）,全部 = 164。

`--user 0` 在单用户下**无区别**。

可用 flag：`-f`（含 apk 路径）、`-i`（含 installer）、`-U`（含 uid）、`--show-versioncode`。

**影响**：解析规则简单,取 `package:` 之后的整行。

## 3. 应用 label 与图标：设备侧拿不到

**问题**：能否只用 adb 拿到应用名称和图标？

**结果**（实测）：

| 途径 | 结果 |
|---|---|
| `dumpsys package <pkg>` | `grep -ci label` = **0**,完全不含 |
| `pm dump <pkg>` | 同样没有 |
| `cmd package dump --checkin` | 没有 |
| `cmd package resolve-activity`（非 --brief） | 只有 `labelRes=0x7f030000 nonLocalizedLabel=null`,是资源 ID 不是字符串 |
| 设备上 `/system/bin` 找 aapt | **为空**,无 aapt/aapt2 |
| `/data/system`、`/data/app` | Permission denied（无 root） |

**唯一可行链路**（实测成功）：

```
pm path <pkg>                  → /data/app/.../base.apk
adb pull                       → 主机临时文件
aapt dump badging              → application-label:'Probe Test App'
                                 application: icon='res/mipmap-mdpi-v4/ic_launcher.png'
                                 application-icon-160/240/320/480/640: ...
```

系统 APK 同样可 pull（`/product/app/Calendar/Calendar.apk`,479 MB/s）。

**影响**：这是一个**新组件依赖（aapt）**,设计文档第五节记录了三个备选方案的权衡,第一版采用内置 aapt。

## 4. adb install 的输出与失败分类

**成功输出**（实测）：

```
stdout: Performing Incremental Install / Success / Install command complete in 31 ms
stderr: All files should be loaded. Notifying the device.
exit:   0
```

`--no-incremental` 时 stdout 为 `Performing Streamed Install` + `Success`。

**失败情形**（全部实测）：

| 情形 | 输出 | exit |
|---|---|---|
| 已存在同签名版本（未加 -r） | **Success** | **0** |
| 签名冲突 | `INSTALL_FAILED_UPDATE_INCOMPATIBLE: ... signatures do not match previously installed version` | 1 |
| 版本降级 | `INSTALL_FAILED_VERSION_DOWNGRADE` | 1 |
| 空间不足 | `java.io.IOException: Requested internal only, but not enough space` | **0** |
| 缺 dex | `INSTALL_FAILED_INVALID_APK: ... code is missing` | 1 |
| 无签名/签名被剥 | `INSTALL_PARSE_FAILED_NO_CERTIFICATES` | 1 |

**两个陷阱**：

1. **空间不足时 exit 仍是 0**,只有 stderr 有内容
2. **同签名版本已存在时返回 Success**（Android 11+）,但实际可能未更新

**影响**：所有安装必须回读 `pm list packages --show-versioncode` 验证版本,不能信 exit code。

## 5. 卸载语义

**结果**（实测,用 debuggable 包写入 `/data/user/0/<pkg>/data_marker.txt`）：

| 命令 | 数据 | UID |
|---|---|---|
| `pm uninstall -k <pkg>` | **保留**（重装后 `run-as ... cat` 仍是原内容） | 不变 |
| `adb uninstall <pkg>` | **删除**（重装后文件不存在） | 变化（u0_a132 → u0_a133） |

卸载不存在的包：两者均 `Failure [DELETE_FAILED_INTERNAL_ERROR]`,exit 1。

**影响**：产品上「卸载」与「彻底删除」必须是两个动作,前者用 `pm uninstall -k`。

## 6. 启动应用的三种方式：失败时退出码都为 0

**结果**（实测）：

| 方式 | 成功 | 失败 | exit |
|---|---|---|---|
| `cmd package resolve-activity --brief <pkg>` | 两行：解析头 + 组件名 | `No activity found` | **0** |
| `monkey -p <pkg> -c android.intent.category.LAUNCHER 1` | `Events injected: 1` | `** No activities found to run, monkey aborted.` | **0** |
| `am start -n <pkg>/<act>` | `Starting: Intent {...}` | `Error type 3` / `Error: Activity class {...} does not exist.` | **0** |

**`resolve-activity --brief` 的输出陷阱**：

```
priority=0 preferredOrder=0 match=0x108000 specificIndex=-1 isDefault=true
com.android.deskclock/.DeskClock
```

第一行是解析头,**组件在最后一行**。

`am start -W` 实测：`Status: ok / LaunchState: COLD / TotalTime: 133 / WaitTime: 135`；已在前台时输出 `Warning: Activity not started, intent has been delivered to currently running top-most instance.`

**影响**：三种方式都必须解析文本判断,不能信 exit code。设计上优先用 `am start -W`（有明确的 Status 字段）。

## 7. 进程标识与停止方式

**进程名**（实测 `ps -axo pid,comm`）：

```
/Users/.../emulator/qemu/darwin-aarch64/qemu-system-aarch64-headless
```

精确匹配：`pgrep -f "qemu-system-aarch64-headless -avd <name>"`。

`emulator` 命令只是 launcher,exec 成 qemu 后 **PID 不变**（实测 launcher pid 67793 与 qemu pid 相同）。

**停止方式对比**（实测）：

| 方式 | 耗时 | 清理 | 快照 |
|---|---|---|---|
| `adb emu kill` | 1-3s | 有 `removeAll` | 会写（未加 -no-snapshot 时） |
| `kill -TERM` | 2s 内 | 有 | 会写 |
| `kill -9` | 0s | 无 | 无 |

`emu kill` 日志：

```
Wait for emulator (pid N) 20 seconds to shutdown gracefully before kill
INFO | Saving snapshot 'default_boot' took 1120 ms
```

**影响**：必须用 `emu kill`（或 TERM）保证清理；统一加 `-no-snapshot` 避免每次关闭产生 1.2 GB 快照文件。

## 8. 端口对应关系

**结果**（实测）：`-port 5580` 启动后 qemu 同时 LISTEN `127.0.0.1:5580`（console）与 `5581`（adb）。serial 为 `emulator-5580`。

反推验证：`adb connect 127.0.0.1:5581` 成功,`adb devices` 中出现 `127.0.0.1:5581`（与 `emulator-5580` 并存,transport_id 不同）。

**规则**：`emulator-<N>` 的 N = console 端口,N+1 = adb 端口。

### adb devices -l 的状态字段

```
device:    emulator-5580  device product:sdk_phone_arm64 model:... transport_id:55
offline:   emulator-5580  offline transport_id:59      ← 无 product/model 字段
```

第 2 列（device/offline/unauthorized）是唯一状态判据。

**unauthorized 未验证**：模拟器 `ro.adb.secure=0`,不会出现该状态,无真机可测。

## 9. 快照机制（为将来预留）

**结果**（实测 android-30 / 2GB RAM）：

```
<AVD>/snapshots/<name>/
  hardware.ini     4.1K
  screenshot.png    49K
  textures.bin     3.5M
  ram.bin          1.9G     ← 与 hw.ramSize 同量级,占绝大部分
  snapshot.pb      1.0K
```

console 命令：`adb emu avd snapshot {list,save,load,del,remap,get,pull,push}`。

`save` 后 `list` 显示 `-- probe_test 65M 2026-11-17 12:07:23`（VM SIZE 口径与磁盘 1.9G 不一致）。

`pull` 只能写进 AVD 目录,给绝对路径会被拒：`KO: <file> must be a bare filename`。

`-snapshot <name>` 加载实测：`Successfully loaded snapshot 'default_boot' using 484 ms`,**guest 就绪 <20ms**（轮询第一次即为 1）,应用仍在。

**影响**：快照能秒级恢复,但单快照约 1.9 GB,且会使状态机多出两个状态。第一版不启用,设计上保留事实字段。

## 10. scrcpy-server 推送与端口方向

**版本**：scrcpy 5.0.1,`/opt/homebrew/Cellar/scrcpy/5.0.1/share/scrcpy/scrcpy-server`（733930 bytes）。

**推送与启动**（实测设备端 cmdline）：

```bash
adb -s <serial> push <scrcpy-server> /data/local/tmp/scrcpy-server
adb -s <serial> shell CLASSPATH=/data/local/tmp/scrcpy-server.jar app_process / \
    com.genymobile.scrcpy.Server 5.0.1 scid=2dd86536 log_level=info video=false audio=false
```

设备上另有 `app_process / com.genymobile.scrcpy.CleanUp` 负责清理。退出后 `/data/local/tmp/scrcpy-server` 自动删除。

**端口方向：默认 reverse,不是 forward。**

```
设备端监听 unix abstract socket: @scrcpy_<scid>（/proc/net/unix 可见）
adb reverse  → host-N localabstract:scrcpy_2da73c46 tcp:27183
host 侧连接   → 127.0.0.1:27183
```

`--force-adb-forward` 时改走 `adb forward`（端口区间 27183-27199）。binary 内有 `'adb reverse' failed, fallback to 'adb forward'`,即先试 reverse 再回落。

**影响**：设计需支持两种方向,默认 reverse（实测可用）。
