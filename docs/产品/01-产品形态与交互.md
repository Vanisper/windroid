# 产品形态与交互

本文回答「做成什么样」。四个域的设计文档回答「怎么实现」——两者不能互相替代：
只有实现没有形态，会做出一堆技术上成立、用户无从下手的部件。

## 一、一句话与三个界面

**Windroid 让 Android 应用以独立的原生窗口运行在用户的桌面上。应用库负责准备运行环境、管理实例和打开应用。**

桌面目标包括 macOS、Linux 和 Windows。当前可用版本和各平台的开发进度见[平台进度](../../README.md#平台进度)。

用户感知到的对象是「一个应用窗口」，不是「一台被镜像的手机」。

| 界面 | 职责 | 出现时机 |
|---|---|---|
| **应用库**（主窗口） | 实例列表、应用网格、安装入口、运行中列表 | 常驻，关闭即退出 |
| **应用窗口** | 一个 Android 应用的独立原生窗口 | 点应用时 |
| **设备视图** | 整台设备的画面（含桌面、设置、系统弹窗） | 按需，独立窗口 |

三者是不同层次：应用库是「能开什么」，应用窗口是「开着的」，设备视图是「设备本身」。

## 二、应用库的结构

侧栏列出每个实例的名称和状态，标出当前实例，并提供新建实例和运行环境入口。选择实例会同步切换以下三个区域。

| 区域 | 可查看或执行的操作 |
|---|---|
| 实例概览 | 查看启动进度和服务状态，启停实例，打开设备视图，选择默认桌面。 |
| 运行中 | 查看 Android 保留的应用任务。已开窗的可聚焦或转入后台，后台应用可恢复窗口。 |
| 应用 | 按来源或自建分组浏览应用，安装 APK，打开应用或使用卡片菜单。 |

### 分组

自上而下：**已安装**（`pm list packages -3`）、**系统应用**（`-s`）、用户自建。

- 进列表的硬条件是声明了 LAUNCHER intent。没有 LAUNCHER 的包（纯库、overlay）
  放进界面没有意义。
- 分组是**用户的决定**，系统应用与用户安装的应用在分组上没有区别，都可以被
  移进任何自建组。来源只决定「默认落在哪」。
- 删自建组时成员回到原组。

实例概览的「选择桌面」列出 Android 为当前用户提供的 HOME 候选，包括只声明 HOME 的桌面。候选优先使用已核实的应用名称，缺少名称时显示包名。选择后以 Android 回读的默认桌面更新界面。

## 三、应用窗口

点应用 → 一个原生窗口，内容是该应用的独立虚拟显示，**不是**整台设备的画面。

每个应用窗口通过专属的 scrcpy 会话创建虚拟显示，并在该显示上启动目标包。设备视图可同时显示主屏。再次打开同一实例中的同一应用时，会聚焦已有窗口。

应用窗口可以自由缩放。窗口大小改变后，Android 会重新布局虚拟显示，过渡期间画面按比例居中。设备视图始终按设备主屏比例显示。[显示与输入契约](../架构/03-流域.md)

## 四、关闭语义

首次关闭仍在运行的应用窗口时，Windroid 在该窗口询问如何处理。

| 选择 | 结果 |
|---|---|
| 保留后台 | 关闭窗口并释放虚拟显示。Android 保留活动任务期间，可从「运行中」恢复窗口。 |
| 完全退出 | 结束本实例中的目标应用，核实进程已停止、最近任务已移除，再关闭窗口。 |
| 取消 | 保留窗口和当前操作。 |

勾选「对所有应用窗口记住我的选择」会保存本次的后台或退出选择。临时选择只作用于当前窗口。

判定顺序即优先级：
1. 应用已不在运行 → 静默收拾，没什么可问的；
2. 窗口异常退出 → 报错优先于策略；
3. 有已记住的策略 → 直接执行；
4. 否则 → 询问。

注意「用户从未选择」与「用户选择了默认值」是两件事，必须用可选值表达，
否则一次未勾选「记住」的临时选择会永久改写偏好。

## 五、首次启动与运行时准备

用户不该知道「SDK」「AVD」「镜像」这些词。首次启动的判断顺序：

1. **自检**：模拟器、adb、系统镜像、scrcpy-server 是否齐备，版本是否匹配；
2. **缺失 → 引导下载**：显示需要下什么、多大、进度如何，可暂停可续传；
3. **齐备但无实例 → 引导创建**：按机器配置推荐一个模板，一键完成；
4. **就绪 → 进应用库**：空库时提示「拖入 APK 开始」，而不是显示一个空网格。

**发布版一律自包含**，运行时放在应用自己的目录里，不读写用户已装的 Android SDK。
开发期可指向系统 SDK，但不作为用户配置项——两种来源混用会产生无法解释的状态差异。

## 六、资源治理

允许多开，但要有边界。三层：

1. **内存预算**取物理内存的一半。创建和启动实例时，将所选模板的内存与当前运行实例的配置内存合计后检查。
2. **空闲冻结**适用于未选中的运行实例。连续 10 分钟无交互、无窗口时，Windroid 停止该实例并回收内存。核实本次停止已保存快照后，侧栏显示「已冻结」。点击「恢复实例」重新启动。
3. **并发上限**为 3 个运行实例、8 个应用窗口。达到上限时，界面给出释放资源的操作提示。

## 七、安装

入口只有两个：拖拽 APK 到应用库、点「添加 APK」。**不注册 Finder 文件关联**
——不抢用户系统里 .apk 的默认打开方式。

失败时把 `INSTALL_FAILED_*` 映射成一句中文原因，同时保留原始输出可展开查看。
**不做自动补救**（不自动重试、不自动去库重打包）：用户需要知道发生了什么，
自动动作会掩盖原因，而且动作本身就是猜测。

## 八、非目标

- 不做投屏工具的形态：主界面不是「一台手机」，是应用库
- 不做插件系统、配置抽象层、跨平台统一图形抽象
- 不追求与 Android Studio 的 AVD 管理功能对齐
- 不在 v1 做：音频面板、通知桥接、剪贴板、多显示器映射

## 九、与里程碑的关系

产品形态决定里程碑。里程碑以「用户能做什么」为终点：

| 切片 | 用户拿到什么 |
|---|---|
| S1 运行时准备 | 首次打开能自检、能装、能建实例 |
| S2 实例管理 | 侧边栏看实例、启停、看真实进度 |
| S3 应用库 | 看到应用网格、能安装 APK |
| S4 应用窗口 | 点应用，独立窗口打开它 |
| S5 关闭语义与运行中 | 关窗可控、运行中可管 |

每一片都以「能亲手用一下」为终点，不以「技术可行性被证明」为终点。
