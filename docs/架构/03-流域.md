# 流域设计

## 本文档边界

本文覆盖 Windroid「流域」的设计：流会话的生命周期、视频数据的接收与解码、帧的呈现交付、输入事件的注入时序，以及与设备域、呈现域的契约。

不覆盖：设备启停与 adb 管理（见 [02-设备域](./02-设备域.md)）、窗口所有权与 UI（见 [04-呈现域](./04-呈现域.md)）。

标注：**实测** = 本机验证；**源码** = 上游源码依据；**推断** = 未验证。

---

## 一、定位

**职责**：把一个 Android 实例的显示内容变成窗口里的帧，把窗口里的用户输入变成设备上的事件。

**不负责**：设备启停（设备域）、窗口创建与关闭（呈现域）。

**粒度**：一个窗口对应一个流会话。同一实例的多个应用窗口，各自继承实例的显示流——**这是关键决策，见第六节**。

---

## 二、为什么必须自研 client

scrcpy 分两半：

| 部分 | 归属 | 我们做什么 |
|---|---|---|
| server（设备端 Java） | 第三方固定产物 | 下载、固定版本、推送、启动 |
| client（主机端） | **我们自己写** | 全部协议处理 |

不用官方 client 的原因不是「重复造轮子」，而是官方 client 是一个独立可执行程序：

- 它自己管理窗口，我们无法获得窗口所有权 → 关闭拦截做不到
- 它自己建立 adb 连接，与设备域的 adb 所有权冲突
- 它的输出是它自己的渲染管线，无法把帧交给我们的 GPU 表面

因此 client 必须自研。server 不需要动——它只是把屏幕编码成 H.264 推出来。

**版本必须严格配对**：server 的第一个参数是 client 版本，与自身版本做字符串相等比较，不等直接退出。协议里没有版本协商字段，不存在「兼容多个 server 版本」的余地。这是 `scrcpy-server` 被定为二级组件（跟 app 版本走）的直接依据。

## 三、流会话状态机

与设备域同构：状态从事实派生，不赋值。

### 事实集

| 事实 | 观测方式 |
|---|---|
| `serverPushed` | server jar 已在设备上 |
| `serverRunning` | server 进程在设备上存活 |
| `socketConnected` | 主机侧 socket 已连接 |
| `handshakeDone` | 已收到 codec metadata |
| `firstFrameDecoded` | 已解出第一帧 |
| `framesFlowing` | 最近 N 秒内收到过帧 |

### 状态映射

```
Idle         无会话
Preparing    推送 server / 建立端口
Connecting   socket 已连,握手未完成
WaitingKey   握手完成,等待第一个关键帧
Live         framesFlowing = true
Degraded     Live 但近期无帧(可能卡顿)
Closed       会话已结束
Failed       错误终止
```

**`WaitingKey` 是独立状态的必要性**：H.264 流必须从关键帧开始解，否则全是花屏。握手完成到第一个关键帧之间可能有一到数秒的空白期。混进 `Connecting` 会让用户误以为连接卡住。

## 四、数据通路

```
设备端                         主机端
┌──────────┐              ┌─────────────────────────┐
│  encoder │──H.264 ──▶   │ socket 读取              │
└──────────┘   (adb        │   ↓                      │
               tunnel)     │ 分帧(按 packet header)   │
                           │   ↓                      │
                           │ 硬解码(HW)               │
                           │   ↓                      │
                           │ 帧上传 GPU               │
                           │   ↓                      │
                           │ 表面渲染                 │
                           └─────────────────────────┘
```

### 三个通道

协议使用最多三个独立 socket，启动时按序建立：

| socket | 方向 | 内容 |
|---|---|---|
| video | 设备 → 主机 | codec id(4B) + session packet(12B) + media packets |
| audio | 设备 → 主机 | codec id(4B) + media packets（无 session packet） |
| control | **双向** | 主机下行输入事件；设备上行剪贴板、ACK、UHID |

control 是唯一双向通道，因此输入注入与视频流完全解耦——**输入不需要等视频**。

### 各段的职责与失败表现

| 段 | 职责 | 失败表现 |
|---|---|---|
| socket 读取 | 收字节流 | `recv ≤ 0` → `Closed`（协议无断开消息,靠 EOF） |
| 分帧 | 按 header 切出完整 packet | header 错误 → `Failed` |
| 解码 | H.264 → 原始帧 | 解码错误 → 请求关键帧 |
| 上传 | CPU → GPU | 慢 → 掉帧 |
| 渲染 | 合成到窗口 | 窗口关闭 → 结束会话 |

**必须区分「掉帧」与「断开」**：掉帧是可恢复的性能问题，断开是终态。混为一谈会让用户看到「连接不稳定」的模糊提示。

## 五、输入注入

### 方向与通道

输入从主机到设备，与视频流反向。

**关键约束**：输入事件的时间戳必须与视频帧的时间戳在同一个时钟域，否则触控会「飘」——用户点到的位置与实际响应位置错位。

### 坐标系：绝对像素，不是归一化

**协议用绝对像素坐标**（i32），并携带 `screen_width` / `screen_height`（u16）作为参照帧尺寸。不是 0–65535 归一化（这一点与直觉相反，实测源码确认）。

设备坐标与窗口坐标不是一回事：窗口可能缩放、可能有黑边、可能被拉伸。**必须做显式的窗口坐标 → 帧坐标变换**，不能假设 1:1。变换参数由呈现域提供（它知道窗口尺寸与内容摆放方式）。

**一个容易踩的坑**：如果发送的 `screen_size` 与设备当前实际分辨率不符（例如设备刚旋转），**事件会被直接丢弃**。因此每次分辨率变化（通过 session packet 感知）后，必须更新本地的坐标系基准。

### 时序

```
用户点击
  → 立即捕获(不等待渲染)
  → 坐标变换
  → 注入设备
```

输入不能等视频帧回来再处理——那会引入一帧的延迟（约 16–33ms），在快速滑动时非常明显。

## 六、多应用与显示：三档能力

### 现状：一个实例只有一块屏幕

Android 实例只有一个默认 display。用户同时打开「微信」和「设置」两个窗口时，设备上只有一个前台应用。

朴素方案是「所有窗口共享一路流」，但这样两个窗口显示的内容相同，用户体验是错的。

### 实测发现的三档能力

调研 scrcpy 协议时发现 server 支持 display 相关参数（见 [实测/03-流域](../实测/03-流域.md) F18）：

```
display_id=<u32>       镜像指定的某块 display
list_displays=true     列出可用 display
new_display=<规格>     创建虚拟 display
```

这给出三档递进方案：

| 档 | 做法 | 体验 | 成本 |
|---|---|---|---|
| **一** | 所有窗口共享默认 display 的一路流 | 多窗口内容相同,只是多个观察点 | 最低 |
| **二** | 每个应用窗口对应一个 `new_display` 虚拟 display | 真正并行,各窗口独立 | 中 |
| **三** | 用户手动选择镜像哪块 display | 灵活但需理解 display 概念 | 低 |

### 第一版：只做第一档，但接口预留

理由：

- 第二档需要验证 Android 能否把不同应用启动到指定 display 上（**未验证**），且每路流都有独立的编解码开销
- 一个实例跑 3 个虚拟 display = 3 路编码，CPU 与内存翻倍

**但接口必须预留**：流会话的标识不应该是「实例」，而应该是 `(instance, displayId)`。这样第二档实现时不需要改接口，只是把 `displayId` 从恒为默认值变成按窗口分配。

### 产品含义（第一档下）

窗口切换应用 = **向设备发送「启动该应用」的命令**，而不是「切换这个窗口显示的内容」。

用户点「设置」窗口 → 设备前台变成设置 → 此时「微信」窗口显示的也是设置。

**这是必须让用户理解的限制**：一台实例就是一台设备，多个窗口是同一屏幕的多个观察点。不能伪装成「每个窗口独立运行一个应用」——那会在用户切来切去时产生严重困惑。

**第二档的前景**：如果 `new_display` 可行，就能实现「每个应用窗口独占一块虚拟 display」，真正做到多窗口并行。这是 M2 阶段的验证目标，也是与竞品的关键差异点。

## 七、与设备域、呈现域的契约

### 设备域 → 流域

| 提供 | 说明 |
|---|---|
| adb 连接 | 流域不直接操作 adb |
| server 推送与启动 | 设备域完成 |
| 设备就绪信号 | 只在 `Ready`/`Streaming` 后允许建会话 |
| 会话计数回传 | 流域上报 `sessionCount` |

### 呈现域 → 流域

| 提供 | 说明 |
|---|---|
| 表面句柄 | 帧要渲染到哪 |
| 窗口尺寸与缩放 | 用于坐标变换 |
| 输入事件 | 原始窗口坐标 |
| 窗口关闭 | 触发会话结束 |

### 流域 → 呈现域

| 提供 | 说明 |
|---|---|
| 帧 | 已解码的帧,交给表面 |
| 流状态 | 用于显示「加载中」「已断开」 |

## 八、M1 的分步策略

| 阶段 | 目标 | 验证什么 |
|---|---|---|
| M1a | 用**官方 scrcpy client** 跑通流,但我们创建窗口 | 窗口所有权是否可行 |
| M1b | 自研 client 完成握手与首帧 | 协议理解是否正确 |
| M1c | 点关闭时拦截,确认后停止 | 关闭流程是否闭环 |

**M1a 的关键是解耦**：先用已知可用的流证明「窗口层」可行，再替换流。如果一开始就自研 client，出问题时无法区分是窗口的问题还是协议的问题。

---

## 九、验收标准

1. 单实例单窗口：帧流畅，输入响应无明显延迟
2. 窗口缩放：坐标变换正确，点击位置准确
3. 设备断开：窗口显示明确的断开状态，不是黑屏卡死
4. 同一实例开两个窗口：第二个窗口不启动第二个流会话
5. 关闭窗口：会话正确结束，设备端 server 进程被清理
