# 设备域设计

## 本文档边界

本文覆盖 Windroid「设备域」的设计：接口形状、事实派生状态机、键空间、应用清单刷新、与流域的生命周期关系。

不覆盖：运行时安装与镜像管理（见 [01-运行环境域](./01-运行环境域.md)）、视频解码与输入注入（属流域）、窗口所有权（属呈现域）。

标注：**实测** = 本机验证；**源码** = 上游源码依据；**推断** = 未验证。证据见 [实测/02-设备域](../实测/02-设备域.md)。

---

## 一、定位

**职责**：一个 Android 实例的唯一写者。持有该实例的状态与应用清单,所有状态变更必须经它。

**不负责**：窗口、视频、输入。

**核心约束**：接口不假设与调用者同进程。当前实现为同进程 actor,但接口形状按「可能拆成独立守护进程」设计——将来拆分不需要改调用方。

---

## 二、接口三件套

```
Command  → 异步投递,返回 Ack { accepted | rejected(reason) }
Event    → 单向推送,单调递增游标
Snapshot → 请求-应答,返回当前完整事实集
```

命令改变事实 → 事实改变触发事件 → 新调用方先用快照对齐再订阅事件。

**为什么不是直接方法调用**：方法调用隐含同步与同进程假设。命令是投递、事件是通知、快照是同步点,这三者跨进程语义不变。

### 命令

| 命令 | 说明 |
|---|---|
| `CreateInstance(spec)` | spec 由运行环境域提供（镜像、模板、存储大小） |
| `DeleteInstance(id)` | 必须已停止 |
| `Start(id)` / `Stop(id)` | 启动 / 优雅停止 |
| `Install(id, apkPath)` | 安装 APK |
| `Uninstall(id, package, keepData)` | 卸载 |
| `RefreshApps(id)` | 重新拉取应用清单 |
| `Launch(id, package)` | 启动 Activity,**不创建窗口** |

`Launch` 归设备域是因为它改变设备状态（有 Activity 在运行）。但**窗口不由设备域创建**——它只发事件,呈现域订阅后建窗口。这保证「窗口所有权」不扩散到设备域。

### 事件

```
InstanceStateChanged(id, from, to, reason)
AppsChanged(id, apps)
Progress(id, phase, detail)
Log(id, stream, line)
```

事件带实例身份。全局事件总线是明确排除的设计,事件从设备域发出,订阅者按实例过滤。

## 三、状态从事实派生

### 事实集

| 事实 | 观测方式 |
|---|---|
| `processAlive` | 进程存在（`qemu-system-<arch>-headless -avd <name>`） |
| `adbVisible` | `adb devices` 中该 serial 处于 `device`（非 offline/unauthorized） |
| `servicesReady` | `service list` 同时含 `activity` / `package` / `window` |
| `bootCompleted` | `getprop sys.boot_completed` == 1 |
| `sessionCount` | 活跃流会话数（由流域上报） |

### 就绪时序（实测,决定状态机的关键）

一次冷启动的相对先后（绝对值随机器状态浮动,只看顺序）：

```
       adbVisible = offline      ← serial 出现但不可用
       adbVisible = true         ← 转为 device
       servicesReady = 2/3       ← pm list packages 此时已成功
       servicesReady = true      ← activity/package/window 三个齐备
       bootCompleted = true      ← 比服务齐备晚约 2 秒
```

**三个反直觉的事实**：

1. `adb wait-for-device` **不能**作为就绪判据——它在 transcport 可用时就返回,而那时系统服务尚未起来。adb 的状态机（`wait-for[-TRANSPORT]-STATE`）只有 device/recovery/sideload/bootloader/disconnect,**没有 booted 类状态**。
2. `pm list packages` 成功**不代表系统可服务**——实测此时三个核心服务只齐了两个,还差一个。此时建立流会话会拿到空画面。
3. `init.svc.bootanim` 在 `-no-boot-anim` 下**恒为 stopped**,不含信息量,不能作为判据。

因此判据必须是：**轮询 `service list` 同时包含 `activity`、`package`、`window`**。

### 与同类项目的对照

调研了 scrcpy、Android Studio、Appium、STF、Maestro、Detox、Tradefed 等十余个项目（详见 [实测/02-设备域](../实测/02-设备域.md) 第 1c 节）。要点：

| 发现 | 影响 |
|---|---|
| 12 个项目中只有 Appium 检查具体服务,且正是 activity/package/window | 与我们的独立实测吻合,交叉验证 |
| Maestro / devil / Tradefed / testrunner 把 pm 就绪作为与 boot flag **并列**条件 | 印证「pm 就绪 ≠ 系统就绪」 |
| 无项目用 logcat 匹配作为判据 | 排除该方案 |
| 超时从 10s 到 10min 不等,多数 60–200s | 我们的超时取 180s（见下） |
| scrcpy 只检查 `state == device` | 它是投屏工具,假定设备已启动,不适用我们的场景 |

### `-delay-adb`：已实测，但不采用

Android Studio 的启动脚本用 `-delay-adb`。实测发现它能让「`device` 可见」与「系统就绪」完全重合（三次采样时刻一致），**假就绪窗口归零**——这也解释了为什么那些只等 `sys.boot_completed` 的项目够用。

代价是首次可操作时刻从 11.9s 推迟到 16.8s，多等约 5 秒。

**不采用**：多 5 秒换「判据简单」不划算，而轮询 `service list` 单次约 20ms。但保留为兜底方案——若某系统版本上服务判据不可靠，可切到 `-delay-adb`。

### 超时设定

```
默认 180 秒
```

依据：多数项目落在 60–200s；本机冷启动约 12–17s，留 10 倍余量覆盖慢机器与首次启动。超时后不直接判失败，而是转入「可能较慢」的诊断状态并保留日志路径（见第七节）。

选这三个服务的理由不是「照抄 Appium」,而是它们直接对应我们要做的事：
- `package` — 应用清单
- `activity` — `am start` 启动应用
- `window` — 显示与表面,scrcpy 出画面依赖

`bootCompleted` 仍保留为事实,但只用于**标记最终稳定**,不作为允许操作的门限。

### 状态映射

```
state = f(facts)

Absent      无实例目录
Stopped     有目录,processAlive = false
Starting    processAlive = true,servicesReady = false
Ready       servicesReady = true,sessionCount = 0
Streaming   servicesReady = true,sessionCount > 0
Stopping    收到 Stop,processAlive 仍为 true
Failed      进程退出且非预期
```

**`Ready` 用 `servicesReady` 作门限**：这是「能实际干活」的最早时刻,比 `bootCompleted` 早约 2 秒且语义更准确（直接对应我们实际调用的服务）。应用清单在 `package` 服务出现时就开始预热,不等 `servicesReady` 全部齐备。

子阶段通过 `Progress.phase` 表达,不扩展状态枚举：

```
waiting-adb   processAlive 但 !adbVisible
warming       adbVisible 但 package 服务未起
starting      服务部分就绪(如 package 已起、window 未起)
```

### 硬约束

**状态不是被赋值的,是被计算的。**

任何变更只能是「事实变了 → 重算 → 若与上次不同则发事件」。禁止任何代码路径直接写状态字段。

这针对 v0 的失败模式：v0 曾在 8 个独立位置给同一个 `phase` 赋值,导致状态与实际脱节且无法定位来源。派生式设计里没有赋值点,只有推导函数,任何状态都能反查是哪个事实导致。

## 四、键空间

所有与应用相关的状态使用 `(instanceID, package)`：

| 状态 | 键 |
|---|---|
| 安装记录 | `(instance, package)` |
| 图标缓存 | `(instance, package, versionCode)` |
| 窗口归属 | `(instance, package)` |
| 分组默认值 | `(instance, package)` |

同一应用可装在多个实例,只带 `package` 的键必然串味。这不是「为将来」——多实例存在时立刻成立。

## 五、应用清单

### 拉取

```
时机:pmReady 后立即(预热) / Install / Uninstall / 用户手动
不做定时轮询
```

不轮询的理由：既浪费,又会让「无操作时列表变化」成为可能,违背「状态从事实派生」的前提。

### 输出格式（实测）

```
pm list packages -3   →  package:com.example.app   (每行一个,无空格)
pm list packages -s   →  package:com.android.deskclock
```

系统/第三方的区分用 Android 自己的定义（`-s` / `-3`）,不发明启发式规则。

### 元信息：需要主机侧 aapt（新的外部依赖）

**实测事实**：设备侧拿不到应用名。

```
dumpsys package <pkg>   →  grep -ci label  = 0     ← 完全没有
pm dump <pkg>           →  同样没有
cmd package resolve-activity → 只有 labelRes=0x7f030000(资源 ID,非字符串)
设备上无 aapt/aapt2     →  /system/bin 下为空
```

唯一可行路径：

```
pm path <pkg>  →  /data/app/.../base.apk
adb pull       →  主机临时文件
aapt dump badging → application-label:'应用名' / icon='res/mipmap.../ic_launcher.png'
```

**这引入一个新组件依赖：aapt**（属 Android build-tools）。已决定**内置 aapt**。

| 方案 | 代价 | 结论 |
|---|---|---|
| **内置 aapt** | 约 2-5 MB,平台相关二进制 | **采用** |
| 自己解析 resources.arsc | 需实现二进制 XML + 资源表解析 | 工作量大且易错 |
| 自有设备端助手返回 label/icon | 需额外推送并维护一个小服务 | M1b 后再评估 |

aapt 归入**一级组件**（与 emulator、platform-tools 同级）：用户不可见、不可选、与 app 版本绑定。它与模拟器一起下载，因此不增加独立的下载流程。

长期改进路径：M1b 自研 client 时本来就要推送自己的设备端 server，届时可加一个返回 label/icon 的查询端点，摆脱 build-tools 依赖。边际成本低，但不是现在的优先事项。

### 图标缓存

持久化到 `~/.windroid/cache/icons/`,键含 `versionCode`——应用更新后自动失效。

列表先以包名占位渲染,label 与 icon 异步补全。200 个应用的实例若同步拉取会阻塞数秒,列表可用性与元信息完整性必须解耦。

## 六、与流域的关系

### adb 连接归设备域

**流域不直接操作 adb。** 需要流会话时向设备域请求,由设备域完成 server 推送与端口建立,再把连接交给流域。

理由：两个域同时操作同一设备的 adb 必然产生时序冲突——例如流域正在建转发时,设备域执行 `pm install`。

### 端口方向是 reverse 不是 forward（实测）

scrcpy 默认用 `adb reverse`：设备端监听 unix abstract socket（`@scrcpy_<scid>`）,host 侧连接 `127.0.0.1:27183`。

```
adb reverse  → host-36 localabstract:scrcpy_2da73c46 tcp:27183
```

失败时回落 `adb forward`。设计上应支持两种方向,默认走 reverse（实测可用）。

### 会话计数驱动状态

流域建立/关闭会话时上报,更新 `sessionCount`,驱动 `Ready ↔ Streaming`。这保证「有没有流在跑」不需要单独标志位——它就是事实之一。

```
Stop 时仍有会话
  → 先通知流域关闭会话
  → 等 sessionCount 归零
  → 再停进程
```

不允许「进程已停但会话仍以为自己活着」。

## 七、adb 输出不是证据（有实测支撑的硬规则）

调研发现**多种失败情形的退出码都是 0**：

| 操作 | 失败时的表现 | 退出码 |
|---|---|---|
| `adb install` 空间不足 | stderr: `not enough space` | **0** |
| `cmd package resolve-activity` 无匹配 | stdout: `No activity found` | **0** |
| `monkey -p` 无 activity | stdout: `No activity found to run` | **0** |
| `am start` 组件不存在 | stderr: `Error type 3` | **0** |

还有反向陷阱：**`adb install` 在「已存在同签名版本」时返回 Success**（Android 11+ 行为）,但实际可能没更新。

因此所有变更类操作必须回读验证：

```
安装后 → pm list packages 含该包(或 --show-versioncode 比对版本)
卸载后 → 不含该包
启动后 → dumpsys activity 显示该包在前台
```

### 安装失败分类映射（实测文本）

| 类别 | 关键 stderr 片段 |
|---|---|
| 签名冲突 | `INSTALL_FAILED_UPDATE_INCOMPATIBLE` + `signatures do not match` |
| 版本降级 | `INSTALL_FAILED_VERSION_DOWNGRADE` |
| 空间不足 | `Requested internal only, but not enough space` |
| 缺 dex | `INSTALL_FAILED_INVALID_APK` + `code is missing` |
| 无签名 | `INSTALL_PARSE_FAILED_NO_CERTIFICATES` |
| 包不存在（卸载） | `DELETE_FAILED_INTERNAL_ERROR` |

分类必须解析文本,不能只看退出码。

## 八、卸载语义

```
pm uninstall -k <pkg>   → 保留数据与 data 目录,UID 不变
adb uninstall <pkg>     → 删除数据,重装后 UID 变化
```

**产品含义**：「卸载」默认应保留数据（用户可能只是暂时移除）,「彻底删除」作为独立选项并明确告知 UID/数据将丢失。不要把两者混成一个「卸载」按钮。

## 九、进程与端口

### 进程标识

```
进程名:qemu-system-<arch>-headless
匹配方式:pgrep -f "qemu-system-aarch64-headless -avd <name>"
注意:emulator 命令只是 launcher,exec 成 qemu 后 PID 不变
```

### 停止方式

```
adb -s <serial> emu kill   → 优雅关闭,~1-3s
kill -TERM <pid>           → 同样走优雅路径
kill -9                    → 无清理
```

**必须用 `emu kill`。** 另外：不加 `-no-snapshot` 时优雅关闭会写快照（约 1.2 GB）,这是非预期的磁盘消耗——第一版统一以 `-no-snapshot` 启动。

### 端口

serial `emulator-N` 中 N 即 console 端口,adb 端口为 N+1。区间与分配规则见 [01-运行环境域](./01-运行环境域.md)。

## 十、并发与串行化

同一实例的所有命令串行（actor 语义）,不同实例可并行。

底层资源仍是共享的：adb server（单进程多设备）、端口区间、磁盘。这些竞争由运行环境域管理,设备域只保证「同一实例内不并发」。

---

## 十一、验收标准

1. 两个实例同时 Streaming,应用列表互不干扰
2. 杀掉一个实例的进程 → 该实例进 Failed 并发事件,另一实例不受影响
3. 连续发 Start（未等完成）→ 第二次被拒绝并说明原因,不产生第二个进程
4. Stop 时有活跃会话 → 会话先关闭,再停进程
5. 安装签名冲突的 APK → 明确报「签名冲突」,能区分于「安装失败」
6. 卸载时选「保留数据」→ 重装后数据仍在

## 十二、已决事项

**aapt 内置**：已确认采用。归入一级组件,与 emulator 同批下载。长期可在 M1b 自研 client 时改为自有设备端助手（那时本来就要推自己的 server,加一个查询端点成本很低）,但不是现在的优先事项。
