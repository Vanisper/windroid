# 设备域设计

## 本文档边界

本文覆盖 Windroid「设备域」的设计：接口形状、事实派生状态机、键空间、应用清单刷新、与流域的生命周期关系。

运行时组件与实例存储见 [01-运行环境域](./01-运行环境域.md)，显示传输与窗口所有权分别见 [03-流域](./03-流域.md) 和 [04-呈现域](./04-呈现域.md)。

标注：**实测** = 本机验证；**源码** = 上游源码依据；**推断** = 未验证。证据见 [实测/02-设备域](../实测/02-设备域.md)。

---

## 一、定位

每个实例有一个设备 actor，是该实例设备事实的唯一写者，持有状态快照与应用清单。宿主按请求中的 `instanceId` 路由命令，切换当前实例不改变已发起操作的目标。

**不负责**：窗口、视频、输入。

**核心约束**：当前实现为同进程 actor。其命令、回执、事件与快照使用可序列化的数据。

---

## 二、接口三件套

```
Command  → 投递给目标 actor，返回 Accepted { seq } 或 Rejected { reason }
Event    → 单向推送,单调递增游标
Snapshot → 请求-应答,返回当前完整事实集
```

命令经准入检查后交给后端执行。`WrongState` 给出当前状态和所需状态，`NotReady` 给出当前状态，后端错误携带错误码和诊断。调用方以快照为起点，按 `seq` 接收更新。

**为什么不是直接方法调用**：方法调用隐含同步与同进程假设。命令是投递、事件是通知、快照是同步点,这三者跨进程语义不变。

### 命令

设备命令由收件 actor 确定实例，参数中省去实例 ID。真实实例由宿主调用运行时登记后挂载 actor。下表使用 `Command` 的 Rust 字段名。[域间契约](../../crates/contract/src/lib.rs)

| 命令 | 说明 |
|---|---|
| `Create { spec }` / `Delete` | 创建时记录模板、镜像和存储规格。已停止或已失败的实例可删除 |
| `Start` / `Stop` | 启动 / 停止该实例。重复启动会被拒绝，已停止或正在停止时重复 `Stop` 为幂等操作 |
| `Install { apk_path }` / `Uninstall { package, keep_data }` | 安装主机 APK / 按指定数据策略卸载 |
| `RefreshApps` | 重新读取应用清单和桌面候选 |
| `Launch { package }` | 在主显示启动 LAUNCHER 组件，并回读前台包及显示 ID |
| `SetDefaultHome { package }` | 从该实例的 HOME 候选设置并核实默认桌面 |
| `ForceStop { package }` / `ClearData { package }` | 结束应用 / 清除应用数据 |

设备命令 `Launch` 面向主显示。应用库打开应用窗时，由流会话在该窗的虚拟显示上发送一次 `START_APP`。

### 事件

```
StateChanged { seq, from, to, phase, facts }
AppsChanged  { seq, apps }
Progress     { seq, phase, detail }
Log          { seq, stream, line }
```

每个 actor 有自己的事件通道和递增游标 `seq`。设备事实变化即发布 `StateChanged`，即使状态枚举未变也能读到新的事实。应用清单、桌面或目录读取状态变化时发布 `AppsChanged`。`Progress` 和 `Log` 是契约预留的事件。

`Snapshot` 含 `id`、`serial`、`state`、`phase`、`facts`、`apps`、`catalogStatus`、`desktop` 和 `seq`。订阅方用快照对齐游标，忽略已覆盖的事件，桌面与目录状态也从快照读取。[设备 actor](../../crates/device/src/lib.rs)

### 可序列化约束的边界

命令、事件与快照只传数据。宿主从实例记录取得 serial 和运行时路径。视频与控制 socket 由流会话持有，宿主只向目标 actor 回报活跃会话数。

## 三、状态从事实派生

### 事实集

| 事实 | 观测方式 |
|---|---|
| `dirExists` / `everLaunched` | 后端有该实例的记录 / 本轮生命周期曾成功启动进程 |
| `processAlive` | 检查本实例持有的模拟器子进程 |
| `adbVisible` | 对目标 serial 的 adb 探测成功，且设备回报的私有 AVD 名与实例记录相符 |
| `services` | `service list` 中 `activity`、`package`、`window` 三个各自独立的布尔值，全部为真即服务就绪 |
| `bootCompleted` | `getprop sys.boot_completed` == 1 |
| `sessionCount` | 宿主按实例回报的、已呈现首帧的活跃显示会话数 |
| `stopRequested` / `bootStalled` / `aborted` | 用户请求停止 / 等待 adb 或服务已超时 / 硬上限已触发终止 |

### 就绪时序（实测,决定状态机的关键）

以下为手工 AVD 以 `-no-snapshot` 冷启动时观测的顺序，绝对值随机器状态浮动。

```
       adb 为 offline            ← serial 出现但不可用
       adb 为 device             ← transport 可用
       核心服务齐备 2/3          ← pm list packages 此时已成功
       核心服务齐备 3/3          ← activity/package/window 三个齐备
       bootCompleted = true      ← 比服务齐备晚约 2 秒
```

**三个反直觉的事实**：

1. `adb wait-for-device` **不能**作为就绪判据——它在 transport 可用时就返回,而那时系统服务尚未起来。adb 的状态机（`wait-for[-TRANSPORT]-STATE`）只有 device/recovery/sideload/bootloader/disconnect,**没有 booted 类状态**。
2. `pm list packages` 成功**不代表系统可服务**——实测此时三个核心服务只齐了两个,还差一个。此时建立流会话可能失败或拿到空画面。
3. `init.svc.bootanim` 在 `-no-boot-anim` 下**恒为 stopped**,不含信息量,不能作为判据。

因此判据必须是：**轮询 `service list` 同时包含 `activity`、`package`、`window`**。

### 与同类项目的对照

调研了 scrcpy、Android Studio、Appium、STF、Maestro、Detox、Tradefed 等十余个项目（详见 [实测/02-设备域](../实测/02-设备域.md) 第 1c 节）。要点：

| 发现 | 影响 |
|---|---|
| 12 个项目中只有 Appium 检查具体服务,且正是 activity/package/window | 与我们的独立实测吻合,交叉验证 |
| Maestro / devil / Tradefed / testrunner 把 pm 就绪作为与 boot flag **并列**条件 | 印证「pm 就绪 ≠ 系统就绪」 |
| 无项目用 logcat 匹配作为判据 | 排除该方案 |
| 超时从 10s 到 10min 不等,多数 60–200s | 我们的超时取 180s（见下） |
| scrcpy 只检查 `state == device` | 它是投屏工具,假定设备已启动,不适用我们的场景 |

### `-delay-adb`：已实测，但不采用

Android Studio 的启动脚本用 `-delay-adb`。实测发现它能让「`device` 可见」与「系统就绪」完全重合（三次采样时刻一致），**假就绪窗口归零**——这也解释了为什么那些只等 `sys.boot_completed` 的项目够用。

代价是首次可操作时刻从 11.9s 推迟到 16.8s，多等约 5 秒。

采用 `service list` 轮询以保留这约 5 秒的提前量，本机实测单次查询约 20ms。

### 三层超时与 Stalled 状态

先等 adb，再等三个核心服务。整个启动过程另有累计硬上限。

| 层 | 等待内容 | 默认超时 | 超时说明 |
|---|---|---|---|
| 一 | adb 可用且私有 AVD 身份匹配 | 60s | adb 层问题：端口冲突、目标不符、adbd 未起 |
| 二 | `service list` 含三服务 | 180s | 系统层问题：镜像异常、磁盘慢、内存不足 |
| 硬上限 | 从进程启动累计 | 600s | 防止无限期占资源 |

**分层的价值在于失败归因**：混成单一超时,用户只看到「启动失败」,分不清是网络层还是系统层。

超时依据：多数项目落在 60–200s；本机冷启动 12–17s,留约 10 倍余量。

#### 超时不等于失败

```
Failed   进程已死              真正的失败
Stalled  进程活着但无进展       超时进入这里
```

把慢机器上的正常启动判成失败,会导致用户去重装镜像,而实际只需再等。

界面根据 `phase` 和 `facts.services` 展示当前卡点。例如，adb 已识别、`package` 已起而 `window` 未起时，实例仍可继续等待或停止。当前原生版本的模拟器输出在实例目录的 `emulator.log`。按启动定位失败、跨日读取历史及与宿主日志的关联见[诊断日志](./诊断日志.md)。

「卡在哪一步」是核心信息——`adb` 未出现与 `window` 未就绪,用户的应对完全不同。

#### 退出 Stalled 的条件

| 条件 | 结果 |
|---|---|
| 进程意外退出 | → `Failed` |
| 用户点停止 | 进程仍在退出时为 `Stopping`，确认退出后为 `Stopped` |
| 累计超过硬上限 | 触发终止，进程退出后为 `Failed` |
| 三个核心服务齐备 | → `Ready` |

继续等待期间仍沿用本轮启动的硬上限。

#### Stalled 仍占用资源

`Stalled` 实例仍占用内存、端口与磁盘，可用 `Stop` 停止。端口对随实例登记，停止后仍留给同一实例。

选这三个服务的理由不是「照抄 Appium」,而是它们直接对应我们要做的事：
- `package` — 应用清单
- `activity` — 启动应用与查询任务
- `window` — 显示与表面,scrcpy 出画面依赖

`bootCompleted` 仍保留为事实,但只用于**标记最终稳定**,不作为允许操作的门限。

### 状态映射

```
state = f(facts)

Absent      无实例目录
Stopped     有目录，进程未运行（尚未启动或预期退出）
Starting    进程存活，服务未齐备，未超时
Stalled     启动等待超时，但进程仍存活
Ready       三服务齐备，sessionCount = 0
Streaming   三服务齐备，sessionCount > 0
Stopping    收到 Stop，进程仍在退出
Failed      意外退出，或触发硬上限后退出
```

**`Ready` 以三个核心服务齐备为门限**。实测比 `bootCompleted` 早约 2 秒。后端从这时开始首次读取应用清单。

启动子阶段通过快照和 `StateChanged` 的 `phase` 表达，状态枚举保持不变。

```
waiting-adb   processAlive 但 !adbVisible
warming       adbVisible 但 package 服务未起
starting      服务部分就绪(如 package 已起、window 未起)
```

### 硬约束

**状态不是被赋值的,是被计算的。**

事实变化后，actor 通过 `State::of(facts)` 重算状态，更新快照并发事件。进程存活时优先处理停止请求，进程退出后以退出原因区分 `Stopped` 和 `Failed`。

每个派生状态都能追溯到构成它的进程、连接或设备服务事实。

## 四、键空间

实例清单保存稳定的 `InstanceId`、显示名、规格、私有 AVD 名和 console 端口。宿主保存当前选择，重新打开应用时按注册表加载实例。serial 可能在删除实例后被复用，执行有副作用的 adb 操作前须核对 `ro.boot.qemu.avd_name`。

| 状态 | 键 |
|---|---|
| 应用清单项及其 Android 包来源 | `(instanceId, package)` |
| 应用名称缓存 | `(instanceId, package)`，复用时核对完整版本号和 APK 安装路径 |
| 应用窗 / 设备窗 | `(instanceId, Some(package))` / `(instanceId, None)` |

同一应用可装在多个实例，只带 `package` 的键会混用不同实例的状态。

## 五、应用清单

### 拉取

三个核心服务齐备后首次读取。安装成功或结果待核实、卸载成功、设置默认桌面或清除应用数据后，后端会刷新清单。用户也可手动刷新。读取失败时保留上次结果并重试。

快照中的 `catalogStatus.kind` 为 `pending`、`ready` 或 `failed`，失败时附 `message`。只有成功读到的空清单才表示没有可启动应用。

### 输出格式（实测）

```
pm list packages -3   →  package:com.example.app   (每行一个,无空格)
pm list packages -s   →  package:com.android.deskclock
```

以用户 0 的 `-s` / `-3` 判定系统包和用户包，与 `MAIN` + `LAUNCHER` 查询结果取交集、按包名去重。宿主据此展示「系统应用」和「已安装」。`AppEntry` 含 `package`、`system`、`launcher`、可选的 `label` 和 `iconKey`。

原生宿主另行保存用户自建分组。按来源展示时直接使用应用清单的 `system` 字段，读取既有工作区时保留其分组文件。[宿主分组存储](../../crates/host/src/groups.rs)

`MAIN` + `HOME` 单独查询。`desktop.candidates` 可包含只声明 HOME 的桌面，`desktop.candidateLabels` 保存已核实的候选名称。只有实际解析到候选包时，`desktop.default` 才有值。设置默认桌面后在同一用户回读目标包。[设备目录查询](../../crates/runtime/src/catalog.rs)

### 元信息：主机侧 aapt

**实测事实**：在所测镜像中，常用设备查询只给出资源 ID 或包名。

```
dumpsys package <pkg>   →  grep -ci label  = 0     ← 完全没有
pm dump <pkg>           →  同样没有
cmd package resolve-activity → 只有 labelRes=0x7f030000(资源 ID,非字符串)
设备上无 aapt/aapt2     →  /system/bin 下为空
```

当前从用户 0 的包索引取得已安装的 APK 路径，按需用 `adb pull` 拉到主机临时目录。运行时的 `aapt dump badging` 优先取中文标签，再取默认标签，必要时从 manifest 读取字面量。

### 名称缓存

名称缓存在数据根目录的 `cache/labels/`。每次刷新先核对实例、包名、完整 `versionCode` 和路径，新拉取的 APK 在发布名称前再核对一次。解析失败或本轮时间用尽时，界面回退到包名，下次刷新再尝试。`iconKey` 在当前清单中为空，应用卡片用名称首字符占位。[名称解析与缓存](../../crates/runtime/src/labels.rs)

## 六、与流域的关系

### adb 连接与端口方向

设备窗使用主显示 0，应用窗各用一个虚拟显示。流域为每条显示会话独立推送 scrcpy-server 5.0.1，由目标 serial 上的 `adb forward` 将动态本机端口 `tcp:0` 映射到 `localabstract:scrcpy_<scid>`，供视频和控制连接使用。握手、输入和会话资源回收见 [03-流域](./03-流域.md)。

### 会话计数驱动状态

窗口实际绘出首帧后，宿主按窗口键记一次，关闭时移除。宿主将该实例已呈现的活跃窗口总数上报给 actor 的 `set_session_count`。首个窗口计入时 `Ready → Streaming`，最后一个计数窗口关闭后回到 `Ready`。

即使 `sessionCount > 0`，`Stop` 也直接交给运行时停止本实例的进程。停止成功或观测到进程退出后，会话数归零。宿主清理该实例的窗口、任务和会话记录，请求窗口层整批关闭，并忽略旧窗口回报。停止被拒绝则保留活动窗口。[宿主窗口事件处理](../../crates/host/src/library/observation.rs)

## 七、adb 输出不是证据（有实测支撑的硬规则）

调研发现**多种失败情形的退出码都是 0**：

| 操作 | 失败时的表现 | 退出码 |
|---|---|---|
| `adb install` 空间不足 | stderr: `not enough space` | **0** |
| `cmd package resolve-activity` 无匹配 | stdout: `No activity found` | **0** |
| `monkey -p` 无 activity | stdout: `No activity found to run` | **0** |
| `am start` 组件不存在 | stderr: `Error type 3` | **0** |

实测中，同签名同版本重复安装也可能返回 `Success`。应用库把文件选择绑定到发起安装的实例，切换实例后仍在原目标执行。

1. 主机 `aapt dump xmltree` 从 APK 清单取得包名和 64 位版本号（含 `versionCodeMajor`）。
2. 对目标 serial 执行 `adb install --no-incremental -r --user 0`，检查退出码和两路输出中的失败诊断。
3. 收到 `Success` 且 `pm list packages --show-versioncode --user 0` 回读到完全匹配的包名与版本号，才报告安装成功。无 LAUNCHER 的包同样核实，仍留在网格之外。通信中断、缺少回执或版本不符时报结果待核实，并重新读取清单。

卸载也须在有效的用户 0 包索引中确认包已消失。应用启动则回读目标显示上的任务。[APK 操作与包索引核验](../../crates/runtime/src/install.rs)

### 安装失败分类映射（实测文本）

| 类别 | 输出中的诊断片段 |
|---|---|
| 签名冲突 | `INSTALL_FAILED_UPDATE_INCOMPATIBLE` + `signatures do not match` |
| 版本降级 | `INSTALL_FAILED_VERSION_DOWNGRADE` |
| 空间不足 | `Requested internal only, but not enough space` |
| 缺 dex | `INSTALL_FAILED_INVALID_APK` + `code is missing` |
| 无签名 | `INSTALL_PARSE_FAILED_NO_CERTIFICATES` |
| 包不存在（卸载） | `DELETE_FAILED_INTERNAL_ERROR` |

分类时同时解析 stdout、stderr，保留具体诊断。`DELETE_FAILED_INTERNAL_ERROR` 还需回读包索引才能区分包不存在或设备拒绝卸载。

## 八、卸载语义

```
pm uninstall -k <pkg>   → 保留数据与 data 目录,UID 不变
adb uninstall <pkg>     → 删除数据,重装后 UID 变化
```

以上为重装同一测试包后的实测结果。设备命令用 `keep_data` 明确选择两种语义。

## 九、进程与端口

### 进程标识

历史实测中 `emulator` launcher 执行 `qemu-system-<arch>-headless` 后 PID 保持不变。当前运行时持有本实例的子进程句柄、独占运行锁和进程组，停止前核对进程组归属。

### 停止方式

实测 `emu kill` 与 `SIGTERM` 均可优雅退出并写出快照，`SIGKILL` 无此清理过程。当前运行时向自有进程组发 `SIGTERM`，退出超时后才强制终止。私有 AVD 使用 Quick Boot。

宿主只对未选中、无已开或待开窗口且空闲满 10 分钟的 `Ready` 实例尝试冻结。确认实例已停止且本次优雅退出更新了快照，才显示「已冻结」。缺少保存凭证时显示已停止并报告原因。冻结标记属于宿主，设备状态为 `Stopped`。

### 端口

serial `emulator-N` 中 N 即 console 端口,adb 端口为 N+1。区间与分配规则见 [01-运行环境域](./01-运行环境域.md)。

## 十、并发与串行化

同一实例的设备命令在 actor 内串行，不同实例可并行。宿主为各实例维护独立命令队列。安装 A 的 APK 时仍可切换并操作 B。

adb server、端口区间与磁盘是共享资源。宿主在创建与启动时核对实例内存预算，启动时另检查同时运行的实例数。私有存储与端口分配见 [01-运行环境域](./01-运行环境域.md)。

## 十一、验收标准

1. 两个实例同时 Streaming，应用列表、名称和窗口归属互不干扰。
2. 杀掉一个实例的进程 → 该实例进 Failed 并发事件，另一实例不受影响。
3. 连续发 Start（未等完成）→ 第二次被拒绝并说明原因，不产生第二个进程。
4. 有已呈现首帧的窗口时 Stop → 本实例退出、会话归零、窗口与任务记录清理，其他实例继续运行。
5. 安装同包同版本但签名不同的 APK → 报签名冲突并保留原应用。无 LAUNCHER 的 APK 也需核实完整版本号。
6. 调用保留数据的卸载命令 → 重装后可读到原数据。

打包版 Android 14 中，Alpha 与 Beta 均回读为版本 1，无 LAUNCHER 的测试包回读为 4294967298。[安装与默认桌面实测](../实测/02-设备域.md)

状态转换与会话隔离可分别通过 [actor 回归](../../crates/device/tests/actor.rs) 和 [宿主回归](../../crates/host/src/library/tests.rs) 复验。
