# 呈现域设计

## 本文档边界

本文覆盖 Windroid「呈现域」的设计：前端与表面的分层、窗口所有权、关闭拦截、窗口与应用映射、输入事件转发契约、跨平台表面策略。

不覆盖：流协议（见 [03-流域](./03-流域.md)）、设备管理（见 [02-设备域](./02-设备域.md)）。

标注：**实测** = 本机验证；**推断** = 未验证。框架相关的实现细节待 M0 spike 结论，本文第八节列出待定项。

---

## 一、定位

**职责**：把流域产出的帧变成用户看到的窗口，把用户的操作变成发往设备域的意图。

**内部两层**：

| 层 | 内容 | 变化频率 |
|---|---|---|
| **前端** | 应用库、分组、搜索、设置、TV 布局、状态展示 | 高——产品迭代主要在这里 |
| **表面** | 窗口创建与所有权、视频表面挂载、输入捕获、关闭拦截 | 低——但每个平台各写一份 |

**可分性约束**：前端可整体替换而不影响表面。表面提供的能力与平台无关地描述，逐平台实现。

---

## 二、为什么必须分层

混在一起的直接后果是：改一个列表的排序规则要动平台代码，加一个平台要重写 UI 逻辑。

v0 的失败模式是平台代码里散落着 UI 逻辑——窗口管理、状态展示、布局计算混在同一个文件里，任何界面调整都变成跨层改动。

分层的判据很简单：**前端不 import 任何平台 API，表面不含任何产品语义**。

---

## 三、窗口所有权（本域的核心约束）

### 必须由我们创建窗口

不是接管别人的窗口，也不是复用现成的投屏窗口。

**理由：关闭拦截需要它。** 只有当窗口归属于我们，才能拦截「用户点了关闭」这个动作，并决定后续行为。如果流由官方 scrcpy client 提供，窗口属于它，我们无法拦截——这正是不能用官方 client 的原因。

### 关闭拦截不是「阻止关闭」

拦截的目的是**问清楚用户想干什么**，而不是拒绝关闭。

可选的关闭策略：

| 策略 | 行为 |
|---|---|
| 停止应用 | 结束应用进程，关闭窗口 |
| 隐藏窗口 | 应用在后台继续运行，窗口暂时消失 |
| 关闭窗口，保留实例 | 窗口关闭，Android 实例仍运行 |
| 每次询问 | 弹出选择，可记住本次选择 |

### 一个必须避免的设计

**静默「最小化到后台继续运行」是欺骗性的。** 用户点了关闭，窗口消失了，但应用还在后台占用内存和 CPU，用户不知道。

如果默认策略是隐藏，必须在界面上**显式告知**：「应用将在后台继续运行」，并提供入口让用户找到它。v0 在这点上做错过——用户点关闭后窗口消失，却没有任何提示应用仍在运行。

---

## 四、窗口与应用的映射

### 第一版：一个应用一个窗口

键是 `(instance, package)`，不是 `package`。

同一个应用装在两个实例上 → 两个独立窗口，互不干扰。这与设备域的键空间一致，不是巧合：窗口是「某个实例上的某个应用」的呈现。

### 同一应用重复打开

已存在窗口时，点击应用图标应该**聚焦已有窗口**，而不是再开一个。再开一个会得到两块内容完全相同的屏幕（见第五节）。

---

## 五、多窗口与显示的关系

### 第一版：所有窗口共享一块显示

一个 Android 实例只有一块默认屏幕。多个窗口是**同一块屏幕的多个观察点**。

产品含义必须让用户理解：

```
点「设置」窗口
  → 向设备发送「启动设置」
  → 设备前台变成设置
  → 此时「微信」窗口里显示的也是设置
```

**不能伪装成「每个窗口独立运行一个应用」**——用户来回切换时会严重困惑。

### 预留：每窗口独占显示

Android 支持创建虚拟 display（`new_display`）。如果能把不同应用启动到不同 display，就能实现真正的多窗口并行。

**接口按 `(instance, displayId)` 设计**，第一版 `displayId` 恒为默认值。第二档实现时只是把它变成按窗口分配，不需要改接口。

是否可行**尚未验证**，列为 M2 的验证目标。

## 六、输入事件转发契约

### 分工

```
呈现域：捕获原始窗口坐标 → 原样交给流域
流域：  坐标变换 → 注入设备
```

### 为什么变换不在呈现域做

呈现域不知道设备当前分辨率，而且这个分辨率会变——设备旋转时，server 会重发 session packet 告知新的编码尺寸。

**如果呈现域自己缓存了分辨率并做变换，旋转后就全错了。** 而协议规定：发送的 `screen_size` 与实际不符时，事件会被**静默丢弃**——用户会看到点击毫无反应，却没有任何错误提示。

因此：呈现域只提供「窗口坐标 + 窗口内容区域尺寸」，变换由流域在注入前用最新的分辨率完成。

### 呈现域必须提供的信息

| 信息 | 用途 |
|---|---|
| 窗口坐标 | 原始点击位置 |
| 内容区域矩形 | 排除标题栏、黑边、letterbox |
| 窗口缩放比 | 用户可能拉伸窗口 |

## 七、跨平台表面策略

### 平台顺序

| 平台 | 理由 |
|---|---|
| macOS | 开发机所在平台，能实测 |
| Linux | TV 目标场景，且 CI 友好 |
| Windows | 无本地测试机，最后做 |

### 各平台需要的能力

表面层对每个平台需要的原语是一致的，具体 API 不同：

| 能力 | 用途 |
|---|---|
| 创建窗口并持有所有权 | 关闭拦截的前提 |
| 挂载原生表面 | 视频帧渲染目标 |
| 拦截关闭请求 | 决定后续行为 |
| 捕获输入事件 | 鼠标、键盘、滚轮、触控板 |
| 查询 DPI 缩放 | 高 DPI 屏幕的坐标换算 |
| 全屏切换 | TV 场景 |

**不做跨平台统一图形抽象层**（总览第 8 节已明确排除）。表面按平台原生实现，不追求伪统一——过度抽象会让每个平台都做不到平台原生的事。

## 八、待 M0 spike 决定的部分

以下内容依赖框架选型，当前不写结论：

| 项目 | 待验证 | 若不成立的影响 |
|---|---|---|
| 框架能否拦截窗口关闭 | **否决项**：不能则不考虑 | 换框架 |
| 1080p/30fps 帧上传的 CPU 占用 | 单核 40% 以下 | 降分辨率/降帧率/换框架 |
| 事件循环归谁 | 我们的解码线程能否与 UI 线程共存 | 需要跨线程传递帧 |
| 重绘模型 | 是按需重绘还是持续渲染 | 影响功耗与延迟 |
| 原生表面挂载方式 | 是否有公开 API | 可能需要绕过框架 |

**选型原则**：优先选「能提供原生表面 + 能拦截关闭」的方案，而不只是「UI 写起来舒服」。这是一个需要嵌视频的程序，不是普通 GUI 应用。

---

## 九、验收标准

1. 点击应用图标 → 窗口出现并有画面
2. 点窗口关闭 → 出现策略选择，不静默消失
3. 高 DPI 屏上点击位置准确（坐标变换正确）
4. 设备旋转后点击仍然准确
5. 同一应用重复点击 → 聚焦已有窗口，不开第二个
6. 两个实例的同一应用 → 两个独立窗口，互不影响
