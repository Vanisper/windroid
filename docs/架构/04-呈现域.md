# 呈现域设计

## 本文档边界

本文覆盖 Windroid「呈现域」的设计：前端与表面的分层、窗口所有权、关闭拦截、窗口与应用映射、输入事件转发契约、跨平台表面策略。

不覆盖：流协议（见 [03-流域](./03-流域.md)）、设备管理（见 [02-设备域](./02-设备域.md)）。

下文描述当前的 macOS 窗口实现。第八节另列框架原型的实测数据和跨平台待验证项。

---

## 一、定位

本域在原生窗口中显示流域产出的帧。应用库操作进入实例协调器，视频画布的输入进入所属窗口的控制通道。

**内部两层**：

| 层 | 内容 | 变化频率 |
|---|---|---|
| **前端** | 运行环境准备、实例切换、应用清单和运行状态 | 随产品交互迭代 |
| **表面** | 窗口创建与所有权、视频表面挂载、输入捕获、关闭拦截 | 低——但每个平台各写一份 |

**可分性约束**：前端可整体替换而不影响表面。表面提供的能力与平台无关地描述，逐平台实现。

---

## 二、前端与表面的接口

应用库读取宿主发布的实例快照，通过命令指定操作、实例和目标包。窗口管理器把创建、聚焦、关闭以及会话变化回报给宿主。设备上的任务与本机窗口分别观察，界面据此区分「窗口已打开」与「后台运行」。

---

## 三、窗口所有权（本域的核心约束）

### 原生窗口由 Windroid 创建

窗口管理器为设备视图和每个应用显示创建原生窗口，挂载视频画布，并在用户关闭窗口时协调 Android 会话。

### 应用窗口的关闭选择

用户点关闭时，窗口 delegate 暂缓关闭。默认弹出绑定本窗口的原生选择框。用户可以为全部应用窗口记住「保留后台」或「完全退出」，下次启动继续使用该选择。

「设置 → 应用窗口」通过 `windroid.windowSettings` 读取关闭偏好，调用 `windroid.setWindowSettings({closeAction})` 保存。`closeAction` 可以是 `ask`、`background` 或 `quit`。设置页与关窗选择框共用 AppKit 窗口管理器中的偏好，保存成功会发出携带新值的 `windroid.windowSettingsChanged`。恢复「每次询问」会移除数据目录中的 `preferences/window-close`。

| 选择 | 窗口和 Android 端的行为 |
|---|---|
| 保留后台 | 关闭本窗口，终止本次投屏并释放其虚拟显示。Android 决定后台任务及进程的存活时间，仍在运行的包可从应用库再次打开。 |
| 完全退出 | 请求结束该实例中的目标包并移除任务。操作耗时时窗口显示正在退出，回读成功后关闭。执行失败时保留窗口并显示原因。 |
| 取消 | 继续使用该窗口。 |

设备窗口关闭时直接释放自己的主屏会话。应用库主窗口关闭则退出 Windroid 的主事件循环，统一清理打开的窗口。连接期间关窗会取消尚未完成的启动；选择完全退出时，会先处理在途的启动，再对目标包执行退出。[窗口管理器](../../app/src/windows/mod.rs) · [偏好与状态判断](../../app/src/windows/state.rs)

## 四、窗口映射与复用

窗口键含实例 ID。设备窗口的包名为空，应用窗口另带 Android 包名。用户再次点击同一键会聚焦原窗口。如果上一代窗口正在回收，新请求会在回收结束后创建下一代。过期回调按代号过滤。相同包名跨实例有不同的窗口键。

当前最多同时保留 8 个应用窗口，正在回收的应用窗口也计入上限。设备窗口可独立打开。[窗口注册表与测试](../../app/src/windows/registry.rs)

## 五、画面与运行状态

设备窗口显示实例主屏。应用窗口请求自己的 Android 虚拟显示，在该显示上启动包。每个窗口独占一路数据与控制会话。调整应用窗口尺寸会请求改变其虚拟显示的尺寸，设备窗口则对主屏画面作等比缩放。[流域契约](./03-流域.md)

后台解码线程发布最新 BGRA 帧，由主线程更新所属窗口的 AppKit 表面。设备回读中的包名与显示 ID 用来确认应用仍在该窗口运行。Android 自行退出时，窗口协调器容许 Activity 切换时短暂出现空快照；连续观察到目标消失才结束窗口。[后台工作线程](../../app/src/streaming.rs) · [Activity 检查](../../app/src/windows/state.rs)

## 六、输入事件转发

表面层拥有当前绘出的图像和内容矩形，因此由表面层完成坐标换算。先将 AppKit 窗口点变换到视图局部坐标，再按图像的等比放置矩形换算为帧绝对像素；黑边丢弃。按下、拖动、释放和滚轮事件随附该帧实际宽高。流域检查帧尺寸，旋转或更改尺寸后只注入匹配的事件。按键及文本由有焦点的画布传往其所属控制通道。[表面和输入映射测试](../../crates/host/src/video.rs) · [控制通道](../../crates/stream/src/control.rs)

## 七、跨平台表面策略

### 平台顺序

| 平台 | 当前开发重点 |
|---|---|
| macOS（Apple 芯片） | 首个完整实现。用 AppKit 持有窗口、VideoToolbox 解码。保留真实例的安装、开窗、定向输入和关闭回归。 |
| Linux | 第二个目标，兼顾 TV 场景。选择与宿主架构匹配的模拟器和镜像，验证 KVM 加速，再接入 GTK4 窗口与 H.264 解码。 |
| Windows | 第三个目标。适配 Windows 工具路径、子进程回收和文件访问，验证模拟器加速，再接入 Win32 窗口与 H.264 解码。 |

两个新桌面端采用同一组首轮验收步骤。在目标系统中启动私有实例，同时打开主屏和应用窗口，验证画面、键鼠输入和窗口缩放。随后关闭应用窗口，回读 Android 任务，核实用户选择的后台或退出行为。

### 各平台需要的能力

表面层对每个平台需要的原语是一致的，具体 API 不同：

| 能力 | 用途 |
|---|---|
| 创建窗口并持有所有权 | 关闭拦截的前提 |
| 挂载原生表面 | 视频帧渲染目标 |
| 拦截关闭请求 | 决定后续行为 |
| 捕获输入事件 | 鼠标、键盘、滚轮、触控板 |
| 查询 DPI 缩放 | 高 DPI 屏幕的坐标换算 |
| 全屏切换 | TV 场景 |

**不做跨平台统一图形抽象层**（总览第 8 节已明确排除）。表面按平台原生实现，不追求伪统一——过度抽象会让每个平台都做不到平台原生的事。

## 八、框架选型：nsh

### 结论

采用 [nsh（Native Shell）](https://github.com/longbridge/nsh)，Apache-2.0，Rust 编写，用各平台原生视图渲染（macOS=AppKit，Linux=GTK4，Windows=Win32）。

### 为什么它解决了核心矛盾

初期的候选方案都要在框架内部找 hook 来实现「窗口归我们」和「挂载视频表面」。nsh 从设计上不是这样：

| 能力 | 提供方式 | 我们得到什么 |
|---|---|---|
| 窗口所有权 | `AppView` 是一个 `NSView`，由调用方放进自己的窗口 | 窗口从一开始就是我们的 |
| 关闭拦截 | 标准 `NSWindowDelegate` | 不依赖框架的 hook,用平台原生机制 |
| 视频表面 | **原生组件**：注册一个名字，框架把任意 `NSView` 摆进布局 | 一个可被布局系统摆放的 `CAMetalLayer` 视图 |

官方文档对原生组件的描述是关键：

> a native component is just one more subview in the same hierarchy: there is no layering problem, it clips, scrolls and receives touches like a \`<View>\`

这项原型验证了框架可以承载原生视图。当前应用库使用 nsh 的 AppView，设备和应用视频窗口直接挂载 AppKit 画布，通过 CALayer 的 contents 展示 CGImage。原型的帧上传数据对应下列实测环境。[当前画布实现](../../crates/host/src/video.rs)

### 实测结论（见 [实测/04-呈现域](../实测/04-呈现域.md)）

| 项 | 结果 |
|---|---|
| 我们自己创建窗口 + nsh 嵌入 | ✅ 通过 |
| 拦截 `windowShouldClose` 并拒绝关闭 | ✅ 通过,窗口保持可见 |
| 原生组件承载表面 | ✅ 通过 |
| 1080p BGRA 帧上传 | ✅ **0.36ms/帧,占 30fps 预算的 1.1%** |

### 保留的顾虑

当前使用 nsh 0.5.x。平台评估保留如下。

| 风险 | 对策 |
|---|---|
| API 变动 | 锁定 `0.5.x` 具体小版本；升级时看 changelog 单独评估 |
| Linux / Windows 后端成熟度未验证 | M1 后再验证；若不可用，macOS 部分不受影响 |
| 项目停止维护 | 代码是 Apache-2.0，可 fork；且我们的用法集中（窗口 + 原生组件 + 原生视图渲染），替代成本可控 |

**这是一个需要持续观察的选择，不是一次性决定。**

### 界面实现语言：TSX

**已决定用 TSX**，不采用纯 Rust 写界面。

理由：

- nsh 的 TSX 支持热更新（保存即生效，约 120ms），界面迭代速度远快于 Rust 重编译
- 本项目的界面部分变化频率高（应用库、搜索、设置、TV 布局），正是需要快速迭代的部分
- 表面层（窗口、视频挂载、关闭拦截）仍在 Rust 里，TSX 只负责界面

**代价**：引入 QuickJS 运行时，多一层调试路径。TSX 里的错误栈需要 source map 才能定位到源码——nsh 提供了这个能力，但属于需要熟悉的工具。

**边界**：TSX 不接触窗口与表面，只描述界面并调用 Rust 侧暴露的命令。这条边界保证即使 TSX 层出问题，窗口与流不受影响。

### 未验证（不作为设计依据）

| 事项 | 何时验证 |
|---|---|
| 完整链路（解码→上传→渲染）稳定 30fps | M1b |
| Linux GTK4 / Windows Win32 后端可用性 | M1 后 |
| 长列表与文本密集界面的性能 | M2 |

## 九、验收标准

1. 点击应用图标 → 窗口出现并有画面
2. 关闭应用窗口 → 按已记住的偏好执行，首次关闭时显示选择框；关闭设备窗口后其他显示仍可用
3. 高 DPI 屏上点击位置准确（坐标变换正确）
4. 设备旋转后点击仍然准确
5. 同一应用重复点击 → 聚焦已有窗口，不开第二个
6. 两个实例的同一应用 → 两个独立窗口，互不影响
