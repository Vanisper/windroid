# Windroid 架构总览

Windroid 让用户在自己的电脑上运行 Android 应用，每个应用以独立原生窗口出现。它不是投屏工具：用户感知到的对象是"桌面上的一个应用窗口"，而不是"一台被镜像的手机"。

本文只回答三件事：系统切成哪几块、块之间的依赖方向、哪些约束不容违反。各域的内部设计不在本文展开。

**证据标注**：全文使用三种标记。**[实测]** 有可直接复现的观察支撑，详见 [实测/01-运行环境域](./实测/01-运行环境域.md)；**[规范]** 来自外部规范或第三方源码（scrcpy、Android、adb）；**[推断]** 是本设计基于前两者的判断，尚未实测。

## 1. 从需求推导切分

需求里存在三种性质完全不同的失败。它们不共享故障原因，也不该共享恢复路径：

1. 运行时组件缺失、镜像损坏、端口被占、进程没起来 —— 环境问题；
2. 对同一台 Android 实例的并发状态变更相互覆盖 —— 一致性问题；
3. 解码卡顿、输入时序错乱、窗口关不掉 —— 呈现问题。

按失败域切分，就是让每一类失败有唯一的归属模块和唯一的修复手段。由此得到四个域，依赖顺序固定：

```
        +-----------------------------------------------------------+
        |  呈现域  presentation                                     |
        |    前端 frontend:声明式 UI(应用库/分组/设置/TV)           |
        |    表面 surface:各平台原生(窗口所有权/视频表面/           |
        |                  输入注入)                                |
        +-----------------------------+-----------------------------+
                                      |  依赖只能向下
        +-----------------------------v-----------------------------+
        |  流域  stream(每窗口一个,可多个并行)                      |
        |    解码 / 帧输出 / 输入注入时序                           |
        +-----------------------------+-----------------------------+
                                      |
        +-----------------------------v-----------------------------+
        |  设备域  device(单写者,一个实例一个)                      |
        |    command / event / snapshot                             |
        +-----------------------------+-----------------------------+
                                      |
        +-----------------------------v-----------------------------+
        |  运行环境域  runtime                                      |
        |    运行时组件 / 系统镜像 / 实例存储 / 端口 / 进程         |
        +-----------------------------------------------------------+
```

**依赖规则**：依赖只能单向向下，下层不得反向依赖上层。下层需要通知上层时发 event，不以回调穿透。

**为什么是这个顺序**：

- 运行环境域在最底，因为它只解决"某台 Android 实例存在且可用"，不关心谁在用它。
- 设备域在其上，因为对实例的状态变更必须先有实例；它又在流域之下，因为流的建立与销毁本身就是对设备的变更（启动应用、切换显示），必须经过唯一写者。
- 流域在设备域之上，因为一个流会话只是某台实例上某次显示的消费者；它又在呈现域之下，因为解码与输入时序要被窗口层驱动，而不是反过来驱动窗口。
- 呈现域在最上，因为它可以被整体替换而不动摇下面三层。**[推断]**

## 2. 各域职责与对外形态

| 域 | 负责 | 不负责 | 对外形态 |
|---|---|---|---|
| 运行环境域 | emulator / adb / scrcpy-server 组件、系统镜像、实例存储、端口分配、进程启停 | 应用语义、窗口、解码 | 实例的创建、启动、停止，以及实例的地址与组件版本 |
| 设备域 | 一台 Android 实例的全部状态变更 | 解码、UI、跨实例协调 | 命令、事件、只读快照 |
| 流域 | 一个窗口的视频解码、帧输出、输入注入时序 | 窗口所有权、应用语义 | 帧流与输入通道 |
| 呈现域 | 前端：用户看到的目录与设置；表面：窗口所有权、视频表面、输入注入 | 协议、设备状态 | 平台原生的窗口与视图 |

**设备域的接口形态是硬约束，不是风格选择**：

- **命令（command）**：请求一次状态变更，有明确的结束与明确的失败原因；
- **事件（event）**：状态变化的单向通知，可重放，不携带"请回调我"的引用；
- **只读快照（snapshot）**：任意时刻可整体取出的事实集合；调用方据此渲染，而不是自己累积状态。

由此推出两条实现约束：**[推断]**

1. 设备域**不得假设与调用者同进程**。接口参数与返回值必须可序列化，不得包含共享可变引用、闭包、平台对象（窗口句柄、文件描述符）。
2. 状态只有一份，住在设备域里。上层拿到的是快照，上层不保留自己的权威副本。

这样将来把设备域抽成独立守护进程时，只换传输层，调用方不动。

## 3. 形态 A：单进程

初期是一个进程。设备域以单写者 actor 形式存在：消息队列加内部串行化，全部变更在该 actor 内顺序执行。

不预先拆多进程，理由是多进程会立刻带来 IPC 序列化、生命周期管理与调试三笔成本，而眼下没有必须支付它们的性能或隔离需求。第 2 节的接口约束已经把"可拆分性"预付了——这是买保险，不是提前施工。**[推断]**

## 4. 多实例是一等公民

多实例不是后期功能，它从第一天就改写数据结构。凡是忽略它就要返工的地方，现在必须按多实例写：

| 位置 | 单实例写法（错） | 多实例写法（对） |
|---|---|---|
| 应用键 | `package` | `(instanceID, package)` |
| 窗口归属 | 应用 | 实例 + 应用 |
| 端口 | 常量或随机 | 分配器统一分配并记录占用 |
| 系统镜像 | 可变 | 只读，多实例共享 |
| 实例数据 | 共享目录 | 每实例隔离 |
| 停止实例 | 全局影响 | 只影响该实例及其窗口 |

**所有键必须携带实例身份。** 任何以 `package` 为唯一键的缓存、映射或配置项都是缺陷。

## 5. scrcpy 的不对称性

scrcpy 由两半组成，两半的架构待遇完全不同：**[规范]**

- **server**：设备端的 Java jar，第三方固定产物。我们只做三件事——下载、固定版本、推送。不为它做架构。
- **client**：主机端的协议实现、解码、渲染、输入回传与窗口。**这部分由我们自研**，本项目全部技术难度集中在这里。

因此"接入 scrcpy"不是一个模块，而是横跨流域（协议与解码）与呈现域（表面与输入注入）的能力。

## 6. 技术栈与验证门禁

Rust 为核心。UI 层候选 GPUI，但**必须先通过验证再采用**：验证项至少覆盖窗口所有权、视频表面嵌入、输入事件时序与多窗口并行。验证未通过则更换 UI 层，不影响下面三层。

若 Rust 的学习与推进成本不可接受，Go 是备选。备选的意思是核心语言可换，而第 1 节的依赖顺序与第 2 节的接口形态不随语言改变。**[推断]**

## 7. 必须满足的约束

以下每条都是硬要求。违反任一条的设计不予合入。

1. **单一写者**：状态必须从事实派生，不允许有多个写者各自赋值同一状态字段；一个状态字段只能有一个写入点。
2. **关窗必须确认**：用户点关闭时，若该关闭会终止应用运行，必须先取得确认。静默"最小化到后台继续运行"是欺骗性设计，禁止。
3. **分类沿用 Android 自身**：应用分类以 Android 自身的 intent 类别为准，不自创一套分类体系。**[规范]**
4. **分组由用户决定**：应用来源只提供默认分组值；最终分组是用户的决定，任何刷新不得覆盖用户已做的分组。
5. **窗口所有权归我们**：这是实现关闭前拦截的唯一前提。依赖第三方进程拥有窗口的方案，在该需求上不可能成立。
6. **adb 的输出不是成功证据**：命令返回成功不等于状态已达成，必须回读实际状态验证。**[实测]**
7. **失败要分类**：区分"预期内的环境变化"（设备未就绪、组件缺失、用户切换了实例）与"真正的错误"。前者不打扰用户，后者才上报。
8. **键必须带实例身份**：见第 4 节。

## 8. 非目标

明确不做。出现即为范围蔓延：

- 插件系统；
- 配置抽象层：不为未知平台预留配置面；
- 跨平台统一图形抽象层：表面按平台原生实现，不做伪统一；
- 通用事件总线：事件走设备域，不做全局广播；
- scrcpy 协议的多版本兼容：固定单一版本。

## 9. 里程碑

| 里程碑 | 目标 | 完成判据 |
|---|---|---|
| M0 | 骨架：工具链、命令/事件通道、空窗口 | 能起一个空窗口，命令可往返，事件可送达 |
| M1a | 窗口所有权 | 用官方 scrcpy client 验证：窗口由我们创建时可拦截关闭 |
| M1b | 自有握手 | 自研 client 完成 server 推送、端口转发、连接与首帧 |
| M1c | 关闭拦截 | 点关闭后窗口不关闭，确认后按策略执行 |
| 之后 | 多实例、镜像管理完善、跨平台 | — |

M1a 先用官方 client，是为了把"窗口所有权"与"协议自研"两个风险解耦：先用已知可用的流证明窗口层可行，再替换流。
